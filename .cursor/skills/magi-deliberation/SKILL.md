# MAGI 審議

親エージェント＝マザー。編集の前に結論を出し、**ユーザー承認があるまで** `docs/` を書き換えない。

## ルール順守（必須）

- 親・3 役とも **`.cursor/rules/project-agent.mdc`**（および `.cursor/rules/` 全体）に従う
- 委譲プロンプトに「`project-agent.mdc` を順守すること」と、論点に必要な `docs/` 抜粋（または該当箇所を読む指示）を含める
- `honesty-and-accuracy.mdc` も同様に順守（未読の仕様を「設計では」と言わない）

## 仕様書との距離感

`docs/` は**正本だがまだ案**であり、後から修正・変更があり得る。

- まず現状の設計案・検討事項を読む（無視しない）
- より良い案があれば **提案してよい**。そのとき必ず次を明示する:
  - **現行仕様:** （該当箇所の要約）
  - **相違点:** （何がどう違うか）
  - **提案理由:** （なぜ変える価値があるか）
- 黙って仕様を上書きした体で書かない。統合でも「仕様どおり／仕様と異なる提案」を分けて書く

## 手順

1. **論点を仮置きする**  
   - 対象: `docs/検討事項.md` の項目番号、またはユーザーが指定した論点  
   - 設計案の関連箇所を短く読む（矛盾チェック用）

1.5 **議題妥当性（親・固定前・必須）**  
   次が1つでも「いいえ」なら、**3役を起動せず**ユーザーに差し戻し／議題差し替え案を出す。
   - ユーザー意図と一致するか
   - 1決定単位か（隣接項目を混ぜていないか）
   - 未決で、重複・決定済の再燃でないか
   - 次の実装／未決のブロッカーか（議論のための議論になっていないか）

   OK なら論点を固定して次へ。

2. **3 エージェントを同時起動**（必ず並列・同一ターン）  
   - `melchior` … 保守・リスク  
   - `balthasar` … 体験・面白さ  
   - `casper` … 実装・β現実  
   - 各プロンプトに含めるもの: `project-agent.mdc` 順守指示、論点全文、選択肢表、既存の私案（あれば）、関連する設計抜粋、「仕様と異なる提案は相違を明示してよい」  
   - **任意:** 議題が的はずれ／前提欠けなら所見**先頭に1〜3行**で「議題チャレンジ」と書いてよい。議題の勝手な差し替えはしない。本論は条件付きで書いてよい  
   - カスタム subagent 名が使えるならそれを使う。使えなければ `generalPurpose` を 3 本立て、各 `.cursor/agents/*.md` の本文を役割として渡す  
   - いずれも **readonly / 意見のみ**（ファイル編集させない）

3. **マザーが統合する**（親が書く。編集はまだしない）

   まず **ユーザー向けの要点**（下の「ユーザー向け提示」）を書く。詳細の対比は後ろに回すか省略してよい。

```markdown
## MAGI 統合（要点）
**一言で:** （決める／変えること。1文）
**なぜ:** （1〜2文。専門用語は避けるか直後に言い換える）
**具体的にどうする:** （短い箇条書き or 小さな表）
**あなたへの確認:** （承認してよいか／まだ議論か／議題を差し替えるか）

## 補足（必要なら）
**議題妥当性:** OK / ずれ疑い（理由一言）→ ずれなら推奨を出さず差し戻し
**3 所見の共通点:** （各1行まで）
**対立点:** （あるときだけ。短く）
**仕様との関係:** 現行どおり / 一部相違（相違点を列挙）
**βでの仮決め:** （数値・ロックなど）
**設計案へ移す文案（草案）:** （短く）
**検討事項の更新案:** 状態 / 決定ログ行
```

   **議題妥当性が「ずれ」**のときは、推奨や docs 反映案を出さず差し戻し／差し替えを求める。ユーザーが「この問いでも答えろ」と明示したときだけ続行可（その場合は仮結論・実装パイプライン禁止を明記）。

4. **承認後のみ反映**  
   - 「OK」「設計案へ」「検討事項を更新して」等があれば、最小 diff で  
     - `docs/検討事項.md` の状態・決定ログ  
     - 必要なら `docs/ぷるりんレーサーズ_設計案.md`  
     - 運用のみの決定なら該当スキル／ルール  
   - 承認がなければ草案提示で止める

## ユーザー向け提示（必須）

ユーザーへの最終メッセージは、**読んで決められる短さ**を優先する。

- 先頭は必ず: **一言で / なぜ / 具体的にどうする / 確認**
- 3役所見の長い引用・用語の羅列・飛び飛びの対比表は、要点のあとに回すか省略
- 「詳しく」と言われてから詳細を出す、でよい
- 難解な語を使うなら、直後に日常語で言い換える

## 禁止

- 3 役を Sequential に 1 体だけ動かして「並列した体」にすること
- 議題妥当性チェックをスキップして 3 役を起動すること
- 議題妥当性が「ずれ」のまま統合推奨や実装パイプラインへ進むこと
- 承認前に決定済へ書き換え・設計案へ移すこと
- 3 所見を無視して親の持論だけ書くこと（統合でも所見は必要なら短く対比する）
- ユーザー向けに、飛び飛び・難解なままの長い統合だけを出すこと
- `project-agent.mdc` を無視して審議すること
- 仕様との相違を隠したまま推奨すること
