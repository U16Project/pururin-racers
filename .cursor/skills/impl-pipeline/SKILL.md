# 実装パイプライン

親＝指揮者。

## ルール順守（必須）

- 親および coder / tester / fixer / evaluator は **`.cursor/rules/project-agent.mdc`**（および `.cursor/rules/` 全体）に従う
- 各役へのプロンプトに「`project-agent.mdc` を順守すること」と、必要な `docs/` 参照（パスまたは抜粋）を含める
- 承認・最小 diff・必読コンテキスト・委譲時のコンテキスト渡しは `project-agent.mdc` のとおり

## 仕様書との距離感

`docs/` は**正本だがまだ案**。実装計画の段階では、より良いやり方があれば提案してよい。

- 計画提示時、現行仕様と違う案を出すなら必ず明示する:
  - **現行仕様:** …
  - **相違点:** …
  - **提案理由:** …
- **承認された計画**が仕様と違う場合、実装はその計画に従う（黙って設計案へ戻さない／黙って計画を広げない）
- 仕様変更そのものの docs 反映は、ユーザー承認後に別途（または計画に含めた範囲だけ）

## 前提

- **未承認の実装は始めない。** 計画（触るファイル／触らない／確認方法／スコープ外／仕様との相違の有無）を出し、明示の OK を待つ
- 参照: `docs/ぷるりんレーサーズ_設計案.md` / `docs/検討事項.md`

## 手順

1. **計画提示 → ユーザー承認**（親が行う。仕様相違があれば上記形式で明示）

2. **coder 起動**  
   - `.cursor/agents/coder.md` の役割で実装  
   - プロンプトに: `project-agent.mdc` 順守、承認済み計画全文、関連 docs 参照  
   - 完了報告を受けてから次へ

3. **tester 起動**（readonly）  
   - coder の変更一覧・確認手順下書きを渡す（＋ルール順守指示）  
   - `PASS` → 5 へ  
   - `FAIL` → 4 へ  
   - `BLOCKED`（環境不足等）→ 親がユーザーに確認し、静的チェックのみで評価するか決める

4. **fixer 起動 → tester 再実行**  
   - FAIL の再現手順だけを渡す  
   - ループは **最大 2 回**。それでも FAIL なら親がユーザーに差し戻し

5. **evaluator 起動**（readonly）  
   - 全ラウンドの結果を渡す  
   - 依頼・承認計画・（必要なら）現行仕様との関係を評価させる  
   - 合格／条件付き／差し戻しを出させる

6. **親がユーザーへ最終報告**（evaluator 要約＋残作業）  
   - コミット／プッシュはユーザーが依頼したときだけ

## カスタム subagent が使えない場合

`generalPurpose`（または同等）を役割名付きで起動し、対応する `.cursor/agents/*.md` の本文をシステム役割としてプロンプト先頭に貼る。あわせて `project-agent.mdc` 順守を明記する。

## 禁止

- 承認前に coder を走らせる
- tester / evaluator に本番コードを書かせる
- fixer に「ついでリファクタ」をさせる
- テスト未実行を PASS 扱いにする
- `project-agent.mdc` を無視する
- 仕様と異なる実装方針を、相違の明示なしで進める
