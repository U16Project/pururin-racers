# プルリンレーサーズ：3Dアセット制作・Blender MCP導入検討

**状態:** 接続確認済み・導入検証中（2026/09/15、Codex新規タスクからBlenderシーン情報の取得に成功）
**作成日:** 2026/09/13

この資料は、今後の 3D アセット制作方法と Blender MCP の導入可否を検討するための参照資料である。ゲームのルール計算やオンライン同期を Blender に移すものではない。

## 1. 背景と目標

レースのゴール地点に置く「GOAL!」看板を最初の実験対象とする。目標は、2D 看板ではなく、Godot で軽量に扱える、ポップで可愛い 3D オブジェクトである。

- 丸く、ぷにぷにした玩具・キャンディ調の造形
- GOAL! の文字自体にも厚みを持たせる
- ポール、支柱、横バーは使わない
- 雲、星、王冠、光のリングなどの装飾は必要に応じて加える
- 遠距離でも判別できる大きさ・配色にする
- 生成画像は完成素材ではなく、コンセプトアート／デザインリファレンスとして使う

想定する構成は次の通り。主要パーツを別オブジェクトにしておくと、Godot 側で個別演出を付けやすい。

```text
GOAL_ROOT
 ├─ CloudBase / CloudOutline
 ├─ Text_G / Text_O / Text_A / Text_L / Text_Exclamation
 ├─ Crown
 ├─ Stars
 ├─ DecorativeBalls
 └─ FloatingRings
```

## 2. Blender での制作方針

複雑なスカルプトを前提にせず、単純形状の組み合わせでゲーム用プロップを作る。

| 部品 | 制作案 |
|---|---|
| GOAL! | Blender Text + Extrude + Bevel |
| 雲 | Sphere 等の変形・組み合わせ |
| 星 | 単純な Star Mesh |
| 王冠 | 簡略化した Mesh |
| 小物 | Sphere 等 |
| 浮遊リング | Curve + Bevel |
| 色・質感 | 光沢のある明るいポップカラー |

Blender は形状、マテリアル、原点、パーツ分割までを担当し、浮遊・回転・発光強化・パーティクル等のゲーム演出は Godot 側で担当する。

## 3. 制作経路の候補

### Blender Python

Codex が `bpy` スクリプトを生成し、Blender で実行して `.blend` と `.glb` を出力する方式。一度ジェネレーターを整えれば、GOAL!、START!、CHECK POINT!、FINAL LAP!、順位表示などを同じ規格で量産できる。

### Blender MCP

Codex から Blender に接続し、生成・確認・修正・書き出しまでを対話的に進める方式。候補の `ahujasid/blender-mcp` は、Blender アドオンと MCP サーバーの組み合わせで、シーン操作・マテリアル操作・シーン検査・Blender Python 実行を提供している。README では Blender 3.0 以上、Python 3.10 以上、`uv`／`uvx` を前提にし、Codex への登録例も案内している。

- リポジトリ: <https://github.com/ahujasid/blender-mcp>
- 通信は Blender アドオンと MCP サーバー間のローカル TCP ソケット（既定ポート 9876）
- Codex と Cursor が同じ Blender を同時操作しない
- `BLENDER_MCP_SAFE_MODE=1` を初期検証で有効にする
- テレメトリは初期検証では `DISABLE_TELEMETRY=true` で無効化する
- 実行前に `.blend` を保存し、重要な制作データを直接対象にしない

これは Blender 本体が提供する公式機能ではないコミュニティ製の候補で、リポジトリは MIT ライセンスを掲げている。採用前にライセンス、更新状況、依存パッケージ、実行権限、ネットワークアクセス、テレメトリの扱いを確認する。MCP は便利だが、任意の Blender Python を実行できる機能があるため、信頼できる環境・保存済みデータでのみ使う。

## 4. 現行プロジェクトとの整合

- リポジトリは `client/`（Godot）＋`server/`（Python）＋`shared/`＋`docs/` のモノレポである。
- Godot 4.7 がクライアントの正本。コース寸法の正本は `shared/course_layout_m5.json`。移動は `distance + offset`。クライアントの Path3D／Curve3D は描画用で、オンラインの判定はサーバーが JSON から計算する。
- #22 のアセット配布方針は、チュートリアル・基本コースを同梱し、重い追加アセットをオンデマンド取得して端末保存するハイブリッド方式である。
- Blender は見た目アセットの制作ツールであり、ゴール判定、位置計算、オンライン権威、コースの幾何計算は担当しない。

## 5. 推奨案

**Blender MCP は導入候補として残し、GOAL 看板の小さな実験で採用判断する。** 最初から全自動化や全アセット制作を目指さない。

### 段階的な検証

1. **環境確認**: Blender の実バージョン、`uv`、アドオン導入可否、Codex のローカル MCP 設定、バックアップ手順を確認する。
2. **接続確認**: テスト用 Cube または Text を作成し、シーン検査、保存、GLB 書き出しまでを通す。
3. **GOAL 看板試作**: 雲＋厚み付き文字＋星等を別オブジェクトで生成する。正面視だけでなく、追随カメラ・横視点・遠距離で確認する。
4. **Godot 組み込み**: GLB をクライアントのアセット置き場へ追加し、シーン配置、スケール、原点、発光、浮遊アニメーションを確認する。
5. **再現性確認**: 同じデザイン規格で START／CHECK POINT 等を作り、修正を再実行できるか確認する。

### 採用判定の条件

- 接続から GLB 出力までを、手戻りを含めて安全に再実行できる
- Godot 4.7 で見た目・スケール・マテリアルが安定して読める
- 遠距離の視認性が GOAL 看板の要件を満たす
- パーツ分割を保ったまま、Godot 側で演出を追加できる
- 既存の Cursor 作業や通常の Godot 開発と競合しない
- ファイルサイズ、メッシュ数、マテリアル数がゲーム用途として許容範囲に収まる

## 6. 3D アセットの共通規格（たたき台）

- 全体的に丸く、角を立てすぎない
- ぷにっとした玩具・キャンディ調の質感
- 明るくポップで、背景から分離する配色
- 遠くから形状を判別できるシルエットを優先
- 不要な細部、過剰なテクスチャ、重いシェーダーは避ける
- 主要パーツは別オブジェクト。Godot 側の演出対象を残す
- 形状の基準スケールと原点を統一する
- 物理 Collision は必要な場合だけ追加し、見た目用アセットにルール判定を持たせない
- 画像生成物はデザインの参考に限定し、最終ランタイム素材は Blender／Godot で管理する

## 7. 役割分担案

```text
Codex
 ├─ Godot コード実装
 ├─ Blender MCP を使った 3D 制作
 └─ GLB 配置・Godot 演出・検証

Cursor
 └─ 通常の IDE 作業（ただし同じ Blender インスタンスを同時操作しない）
```

当面は Codex を Blender 制作の担当とし、Cursor と Blender MCP を同時接続しない。MCP が不安定、または導入できない場合でも、同じ設計を Blender Python 方式へ切り替えられるようにする。

## 11. キャラクター顔メッシュ制作に向けた連携方式の再検討

**更新日:** 2026/09/15

### 11.1 再検討の結論

Nene のアニメ調顔メッシュでは、MCP の接続性や一括生成能力よりも、次の工程を確実に回せることを優先する。

```text
参照確認
  → 現在状態の調査
  → 小範囲の編集
  → 正面・45度・側面の確認
  → トポロジー検査
  → 参照との差異確認
  → 修正または Revert
  → 条件を満たした場合のみ Commit
```

AI が「編集した」ことと、「検証済み」「完成した」ことを分けて記録する。自己申告だけで完成扱いにしない。

### 11.2 現在の問題認識

これまでの顔メッシュ試作では、次の問題が発生した。

- 規則的な格子を優先し、目・鼻・口・顎の変形に沿った edge flow が不足した
- 正面の見た目を優先し、45度・側面で鼻、鼻下、唇、顎の前後関係が弱くなった
- 参考にしたと報告しても、実際の接続や密度が独自に簡略化されていた
- 鼻や口の付近に面や pole が不自然に集中した
- 編集直後に AI が完成判定し、Subdivision や表情変形の確認が不足した

したがって、今回の課題は単なる造形調整ではなく、調査・証拠取得・編集・検証・巻き戻しを含む制作手順の問題として扱う。

### 11.3 参照資料の分離

参照資料は、目的ごとに分けて管理する。

1. **Nene の設定画**: 顔立ち、髪型、可愛さ、シルエットの基準
2. **アニメ系ゲームキャラのワイヤーフレーム**: 目、鼻、口、頬、顎の edge flow の基準
3. **ライセンスが明確な無料ベースメッシュ**: 実際の接続、面密度、変形用構造の確認

3/4 の設定画だけで、正確な側面・背面・髪の根元・肩や骨盤の形を決定しない。トポロジー確認には、可能ならワイヤーフレーム画像だけでなく、許諾済みの実メッシュも使う。

### 11.4 トポロジーの判定方針

pole や三角形の存在だけで失格にしない。判断対象は位置と影響とする。

- 目と口の周囲に変形用の閉ループがある
- 鼻、頬、口、顎へ面の流れが連続している
- 目・口など大きく変形する場所に不自然な pole 集中がない
- 口の奥を一点へ大量の面で集約していない
- 三角形や pole が陰影・表情変形を破綻させていない
- Subdivision 後も輪郭と陰影が維持される
- 左右対称、法線、非多様体、重複頂点を検査できる

「規則的な格子ではないこと」自体を目的にせず、変形と面の流れに適した構造であることを確認する。

### 11.5 連携方式の候補評価

#### 第一候補：Blender Agent Bridge

Blender Agent Bridge は、Codex を含む MCP クライアントから、シーン調査、Viewport・検査レンダー等の視覚証拠取得、可逆編集、必要に応じた Blender Python 実行を行う設計である。

- 今回必要な「調査 → 証拠取得 → 編集 → Preview → Commit/Revert」に最も近い
- Codex 専用ではなく、複数の MCP クライアントに接続できる
- Blender 5.2.1 LTS で利用できる可能性は高いが、実環境で接続テストを行う
- トポロジーの良否を自動判定する機能が確認できたわけではないため、構造検査スクリプトと組み合わせる

参照: <https://github.com/CallMeJones/blender-agent-bridge>

#### 第二候補：Codex Blender (`bestmaa/codex-blender`)

構造化コマンド、参照画像の配置、レンダー、比較用コンタクトシート、画像差分、反復レポートを持つため、同じ条件で前後比較する用途に向く。

- 参照画像とレンダーの比較を定型化しやすい
- ローカルの資産・参照画像を管理しやすい
- トポロジー意味論や「可愛いか」の判定は別途必要
- 画像差分は edge flow の正しさを直接検査しない

参照: <https://github.com/bestmaa/codex-blender>

#### 第三候補：DCC-MCP Blender

typed tool と Agent Skill を優先する設計は、巨大な raw Python の一括生成を避け、工程を分割する用途に合う。

- 小さな操作へ分けやすい
- Codex 以外の対応クライアントも想定されている
- 顔トポロジー編集に対する実運用結果は別途検証が必要
- 導入コストが上がるため、先に第一候補と現行方式を比較する

参照: <https://github.com/dcc-mcp/dcc-mcp-blender>

#### 保留：単純な Codex 専用 Blender Bridge / MCP

Codex 対応だけでは採用理由にしない。シーン調査、複数方向の画像取得、構造検査、Preview、Revert のどれが現行方式より改善するかを確認できる場合だけ比較対象にする。

参照: <https://github.com/webita/blender-codex-mcp>

#### 補助方式：MCPを使わない Blender Python / CLI

MCPの代替というより、検査と再現性を担う補助経路として残す。

- mesh 統計、非多様体、対称性、面種別、pole の位置などを JSON に出力する
- Blender の正面・45度・側面レンダーを固定条件で生成する
- Codex が結果を読み、小範囲の修正スクリプトを作る
- MCP が停止しても同じ検証を再実行できる

視覚的な可愛さや形状の判断は、レンダー画像と人間の確認を併用する。

### 11.6 最初の比較テスト

いきなり顔を作り直さず、現在の失敗メッシュを使って読み取り専用の検査を行う。

1. 同じ失敗メッシュ、同じ参照資料、同じ指示文を各方式へ渡す
2. 正面、左右45度、左右側面の画像を取得する
3. 目、鼻、口、頬、顎について、形状上の問題とトポロジー上の問題を分けて報告する
4. edge loop、pole、三角形、面密度、対称性、非多様体を確認する
5. 問題箇所を画像またはオブジェクト情報で示す
6. この段階ではメッシュを変更しない

この検査で、現在の BlenderMCP より正確に問題を見つけられる方式だけを編集テストへ進める。

### 11.7 編集テスト

編集は顔全体ではなく、次のように小範囲で行う。

```text
鼻
  → 正面確認
  → 45度確認
  → 側面確認
  → トポロジー確認

口
  → 同じ検証

頬・顎・目周囲
  → 同じ検証
```

各工程で、変更前・変更後・検証結果・未検証部分を残す。問題が出た場合は Revert し、原因を記録してから次の案へ進む。

### 11.8 合否基準

各方式を、次の観点で比較する。

- シーン状態を正確に読み取れるか
- 必要な方向の画像を取得できるか
- 形状とトポロジーの問題を分けて報告できるか
- 構造検査を再実行できるか
- 小範囲の編集と Preview ができるか
- Revert または Blender の Undo で安全に戻せるか
- 参照と編集結果の比較を残せるか
- Luna または Terra でも検証ループを回せるか
- 所要時間と Codex 使用量が許容範囲か

重大な構造欠陥を残したまま「完成」と報告する方式は不採用とする。単に生成できることだけでは採用条件を満たさない。

### 11.9 当面の実行方針

まず Blender Agent Bridge を読み取り専用の検査テストで評価する。現行の BlenderMCP は比較用に残し、テスト結果が確認できるまで置き換えない。

Bridge の視覚証拠取得だけでトポロジー問題を解決できない場合は、Codex Blender または MCP 非依存の Blender Python 検査器を組み合わせる。最終的な構成は、次の役割分担を基本とする。

```text
MCP / Bridge
  └─ シーン状態取得、画像取得、編集、Preview、Revert

Blender Python 検査器
  └─ mesh構造、対称性、面種別、pole、非多様体の検査

参照パック
  └─ Nene設定画、ワイヤーフレーム、許諾済み実メッシュ

Codex
  └─ 調査結果の解釈、修正範囲の決定、比較、完了判定
```

この方針では、AIの自己判断だけに依存せず、証拠・数値・比較画像・Undo/Revertを揃えてから次の工程へ進む。
