# ぷるりんレーサーズ - ゲーム仕様設計書

## 📖 プロジェクト概要

### 🎯 ゲームコンセプト

かわいい架空生物が、以下の要素を駆使して競うレースゲームです。

- ✅ **育成**: 属性 / ステータス 
- ✅ **戦略**: レース位置取り / ドラフティング / スタミナ管理
- ✅ **条件適応**: どの大会のレースに合わせるか / いつ仕掛けるか / 集団で力を温存するか

世界・物語・呼び方の正本は [`プルリンレーサーズ_世界観設定_v0.1.md`](プルリンレーサーズ_世界観設定_v0.1.md)。

- 生物の名前は **ぷるりん**。レースでは **プル** と呼び、**何プル** と数える
- トレーナーは指示を送るだけで、ぷるりんには乗らない
- 主人公は、異世界小説を書く夢見がちな女の子。デフォルトの名はミオで、ゲーム中の表示には使わない。眠ると異世界の続きの朝に起き、異世界で眠った朝は元の世界に戻る。起きた世界ははっきり思い出せて、もう一方だけがおぼろげになる。起きているあいだ、向こうの日数は進まない。ゲームの中断は、元の世界での目覚めにあたる
- 最初に出会うトレーナーは、仮でヒナタ。ほか6人の仮設定は、世界観設定の「トレーナーたちの仮設定」

### 💡 基本方針

競馬ゲームのように、コースに沿って自動的に前進しながら、以下の要素を楽しみます。

- 📍 **左右移動**: 内側／外側へ位置を調整
- 🌪️ **カーブライン**: カーブでのライン取り
- ⚖️ **速度と旋回の関係**: スピードが高くなるほど制動が難しくなる

**制御方式**:
完全自由移動ではなく、以下の 2 つのパラメータで管理します。

```
distance:    コース開始地点からの進行距離（メイン軸）
offset:      コース中心からの左右位置（単位: m）
```

### 🧭 レース設計思想（重要）

このゲームでは「最適解」を作らない。

状況によって、

- 内側を選ぶ
- 外側を選ぶ
- 集団に残る
- 先頭へ出る

という判断が変化することを目標とする。

**設計理念:**

- コースによって有利な戦術が変わる
- 属性によって得意な状況が変わる
- 位置取りに意味を持たせる
- 集団戦術を成立させる
- 後方一気の戦略も成立させる
- 「最内を走り続けること」が常に正解にならないようにする

※ **風システム（向かい風・追い風・横風）は採用しない。**  
環境要因でレース展開を左右しすぎず、位置取り・集団・コース形状で勝負が決まるようにする。

※ 勝敗を決めるのは **能力配分・属性・脚質・トレーナー判断・レース中判断（ブースト含む）・位置取り**。ガチャ・個体値・ランダム成長、および従順度／トレーナースキル／mistake 系の揺らぎは採用しない（詳細は「トレーナーと NPC AI」）。

## 🏁 レースシステム



### 📊 ステータス・育成システム

限られたポイントを自由配分する育成システム。

ぷるりんの能力は、**プレイヤーが能力ポイントを配分することで決定**する。
能力値による個体差を明確にし、「速度特化型」「スタミナ型」「コーナー型」など、**極端な個性を作れる**ようにする。

#### 📋 基本ステータス一覧


| ステータス | 役割 |
| --- | --- |
| **最高速** | 全力時の推進と抵抗が釣り合う自然到達速度の目安。強制的な速度上限ではなく、空力・ドラフト・疲労で到達域は変わる。表示は時速（km/h）。 |
| **加速力** | 速度を乗せる素早さ。出力走行の比較案では正味加速に応答倍率を掛け、巡航速度や心拍負荷を直接優遇しない。 |
| **スタミナ** | 長距離性能、速度維持能力、残スタミナ量。 |
| **心肺性能** | 心拍の上がりにくさ・下がりやすさ。心拍の共通上限そのものは変えない。 |
| **空力適性** | 空気抵抗への耐性（単独走向き）。 |
| **集団適性** | ドラフティング効果（集団走行向き）。 |
| **接触耐性** | 他キャラや柵との接触時に耐える力。 |
| **操作性** | 左右ライン移動の素早さと走行安定性。接触・急なノッチ変更・ブースト時に生じる心拍上昇やスタミナ負荷を抑え、狙ったラインを保ちやすくする。 |

#### M5以降のパラメータ整理（2026/09/13）

実走テストを踏まえ、**スタートダッシュ・巡航力・ラストスパート**は、M5以降のβでは独立した能力値として積極採用しない。

- 3項目は設計上の概念として残し、将来の拡張候補とする。
- 効果を実装する場合は、脚質やレース状況に応じたボーナス／補正として表現する案を優先する。
- 具体的な発動条件・数値・脚質との対応は、別途のバランス検討で決める。
- 操作性は正式な独立パラメータとして採用する。コーナー性能だけに限定せず、ライン移動・接触・急な出力変更・ブーストに対する走行安定性を表す。
- 上記8項目を正式な基礎ステータスとする。スタートダッシュ・巡航力・ラストスパートは独立ステータスに戻さない。

#### 配分・有効値

- 出走前の配分は各 **1〜10**、8項目の合計 **40点**。初期配分は全項目5で、0は使わない。
- 属性は2項目へ各+2、合計+4する。属性補正を受ける項目だけ、出走前の上限は12になる。
- レース中の有効値は、脚質の順位補正と区間補正を加えた **1〜15**。計算結果も1未満には下げない。
- 正本は `client/data/config/pururin_stats.json` とし、個体保存・レース物理係数への接続は後続作業とする。




#### 💪 育成例

- **速度特化型**: 最高速 / 加速力 / 空力適性 → 短距離・直線勝負に強い
- **スタミナ型**: スタミナ / 心肺性能 / 集団適性 → 長距離・持久戦向き
- **安定型**: 操作性 / 加速力 / 接触耐性 → 混雑・急な仕掛け・テクニカルコースに対応しやすい



#### ❌ 採用しない育成要素

勝敗を「運」ではなく「判断」に寄せるため、以下は採用しない。

- 育成ガチャ
- 個体値
- ランダム成長

能力は **ポイント配分（＋属性ボーナス）で決まる固定値** とする。同じ配分なら、同じ条件では同じ能力として扱う。

### 🎒 所持スロットとレシピ

楽しさの中心は **ポイント配分の取捨選択** にある。所持枠の解放やガチャで枠を増やす進行は設けない。

#### 所持スロット（レースに出せる個体）

| 項目 | 内容 |
|------|------|
| **上限** | **最大 5 体** |
| **解放** | **なし**（最初から最大 5 まで作成・所持できる） |
| **不採用** | ガチャ、ストーリー進行による枠解放、条件付きスロット解放 |

レースへ出走させる個体は、この所持スロットから選ぶ。

#### レシピ（配分テンプレート）

所持とは別に、**レシピ**（仮称）として次の組み合わせを任意に保存できる。

- 能力ポイントの配分
- 脚質
- 属性

| 項目 | 内容 |
|------|------|
| **件数** | ユーザーが望めば多数保存できる（実質困らない件数。厳密な無制限保証は実装時にソフト上限などで調整） |
| **重複** | 配分ポイントの総量は全員同一のため、**同一内容のレシピが複数あってもよい** |
| **用途** | 実験・お気に入り戦術の保管。所持個体への適用・差し替え |

所持＝「いまレースに出せる布陣」、レシピ＝「配分の実験庫／テンプレート」と役割を分ける。

#### 他プレイヤーのデータ

将来は、他プレイヤーのぷるりん／レシピ相当データを **取得・コピー** できるようにする。  
コピー後は自分用に改変してよい。総ポイントが同一なので、完コピ同士が並んでも公平性は壊さない。

※ β では **自アカウント内のレシピ保存・読込・所持への適用** を先行し、他者共有・コピーの本番仕様は後続とする。

### 🏃 レース中の状態値

能力値とは別に、レース中にリアルタイムで変化する値を持つ。


| 状態値 | 内容 |
| ------ | ---- |
| **現在速度** | 現在の走行速度 |
| **出力ノッチ** | ローカル簡易レースの主操作。プレイヤーも CPU も同じ駆動計算にノッチを入れる（-3〜6） |
| **目標スピード** | M5 オンラインで現在使っているペース指示（ローカルは廃止、オンラインも今後ノッチへ揃える予定）。現在速度はこれに向かって追従する |
| **残スタミナ** | 使用可能な体力 |
| **心拍数** | 現在の身体負荷 |
| **モチベーション** | 精神状態、能力発揮率 |
| **出力負荷** | 目標スピード方式で、目標への追従に要する内部負荷（導出値。ノッチ方式ではノッチ自体が出力） |
| **集団位置** | 先頭 / 集団 / 中団 / 後方 |
| **ブースト状態** | 発動中か、冷却状態か |

#### 心拍・スタミナの基本関係（ローカル実装）

- 心拍の共通範囲は `100〜230 bpm`。`200 bpm` までは通常範囲、200を超えるとオーバーヒートとして扱い、230で頭打ちにする。
- 心拍は常に `ノッチ負荷−自然回復` の一つの式で更新する。正のノッチでは設定ファイルのノッチ別基礎心拍上昇率へ負荷倍率を掛け、現在心拍に応じた自然回復を差し引く。低心拍では正味上昇率が大きく、高心拍では自然回復が大きくなってノッチごとの定常域へ収束する。心拍が下がる方向では自然回復倍率 `2.75` を適用する。ノッチ0または負ノッチでは自然回復だけが働き、100 bpmへ漸近する。現行の配列は `[0.0, 1.5, 2.5, 3.48, 4.63, 9.0, 13.0]`（2026/10/03 に仮採用。値と経緯は [`設定管理.md`](設定管理.md)）。ノッチ1〜3は温存・微調整、ノッチ4は長時間では通常上限ごえを意識する巡航、ノッチ5・6は短い勝負どころ用、という役割にしている。ノッチは6段階のままとし、7・8などを追加して操作を細分化しない。
心肺ステータスは最大心拍そのものを変更せず、心拍の上昇速度と回復速度を調整する。

| 心肺ステータス | 走行中の傾向 |
| -------- | ------------- |
| **低心肺型** | 同じノッチで心拍が早く上がり、回復が遅い |
| **標準型**  | 平均的な上昇・回復 |
| **高心肺型** | 心拍が上がりにくく、回復が速い |

### 🔥 ブーストシステム（鞭要素）

競馬の鞭、自転車競技のアタックに相当する仕掛け要素。

#### 基本仕様

- **1 レース最大 3 回**
- **1 回 3 秒**
- 発動中は加速度上昇、および目標スピード／速度上限の一時的な引き上げ（詳細は実装時に一文で固定）
- 心拍数が急上昇し、残スタミナを大量消費

> **現行（ローカル、2026/10/06〜）:** プレイヤーだけ、ブースト（X。1レース3回・1回3秒。押すたびにポイントが入り、ポイントに応じて推進力が増える）と、ダッシュ（B／Zキー。2秒。推進力 +20%＋加速・操作の能力ぶん）を実装済み。CPUは使わない。数字は [`設定管理.md`](設定管理.md) の「ダッシュとブースト」。



#### 連続ブースト

ブースト中に再使用可能。


|           | 内容                          |
| --------- | --------------------------- |
| **メリット**  | 加速度アップ → 一気に前へ出る            |
| **デメリット** | 心拍限界突破 → オーバーヒート時間増加 → 後半失速 |




#### 戦略例


| 仕掛け方         | メリット   | デメリット      |
| ------------ | ------ | ---------- |
| **早仕掛け**     | 位置を取れる | ゴール前失速のリスク |
| **最終直線ブースト** | 最大効果   | 前が詰まる可能性   |

### 🏇 脚質システム

脚質は**レース方針**であり、能力値ではない。


| 脚質     | 特徴        |
| ------ | --------- |
| **逃げ** | 先頭維持、序盤強い |
| **先行** | 前方集団で戦う   |
| **差し** | 集団内で温存    |
| **追込** | 後方待機、終盤勝負 |




#### 脚質ボーナス（順位・区間）

脚質はレース方針であり、順位と距離区間に応じて有効ステータスを決定的に補正する。

| 脚質 | 適正順位（8プル） | 適正順位時 | 第1〜4区間のボーナス |
| --- | --- | --- | --- |
| **逃げ** | 1〜2位 | 全8項目 +1 | 第1区間：加速力 +2 |
| **先行** | 3〜4位 | 全8項目 +1 | 第2区間：空力適性 +2 |
| **差し** | 5〜6位 | 全8項目 +1 | 第3区間：集団適性 +2 |
| **追込** | 7〜8位 | 全8項目 +1 | 第4区間：加速力 +2 |

- 隣の順位組なら補正0、2組以上離れたら全8項目 -1。
- 順位補正は即時反映する。境界での安定化は、実走で必要になった場合にだけ検討する。
- 出る人数が8プルと違うレースでは、適正順位を式で決める（2026/10/08）。適正順位は、いつも続きの順位で、数は 8プルまでは2つ、9〜12プルは3つ（`max(2, 切り上げ(人数 ÷ 4))`）。逃げはいつも上から、追込はいつも下から、先行と差しはその間を均等に割った位置。2プルなら全脚質が1〜2位、3プルなら逃げ・先行が1〜2位で差し・追込が2〜3位、4プルなら逃げ1〜2位・先行と差し2〜3位・追込3〜4位。適正順位から「適正順位の数」以内なら補正0、それより離れたら −1。人数ごとの表は [`設定管理.md`](設定管理.md)。
- モチベーションはレース性能を上下させる独立値には採用しない。脚質・順位・区間、心拍、スタミナ、接触などの見える状態で性能変化を表現する。

### 💨 ドラフティング（空気抵抗軽減）システム

前方の生物の後ろにつくことで空気抵抗を減らす。自転車競技のように機能する。

**計算基準:** 前方生物との位置関係のみ。気象・風向きは使わない。

#### 📊 空気抵抗率（例）


| ポジション    | 空気抵抗率    |
| -------- | -------- |
| **先頭**   | 100%（基本） |
| **2 番手** | 80%      |
| **集団中央** | 60～70%   |
| **最後尾**  | 50～60%   |




#### ✅ ドラフティングの効果

- スタミナ消費減少
- 速度維持
- 終盤のスパート用にスタミナを温存



#### 🏃‍♂️ 先頭走行のメリット例

- わずかな速度上昇
- 観客による気力上昇
- 逃げ成功ボーナス

## 🛣️ コース移動方式



### 📍 位置管理の基本（distance + offset）

```yaml
distance:
  unit: meter
  meaning: コース開始地点からの進行距離

offset:
  unit: meter
  min: -6.0   # 内側
  max: +6.0   # 外側
```

- **負の offset**: 内側
- **正の offset**: 外側
- 実際の可動範囲はコース幅に合わせてクランプする
- 現行の標準コースは全幅 **15 m**、機体の直径 **1.5 m**。中心からはみ出さない範囲は **±6.75 m**。上の ±6.0 は説明用の丸め

**位置決定の流れ:**

```
distance = 500m
↓
Curve3D から 500m 地点の座標を取得
↓
その地点の中心位置 + offset（左右）
↓
キャラクター位置決定
```

### 📐 生物サイズとコース幅（最大 12プル対応）

**コース幅・ゲート素材は最大 12プルまで対応できるサイズで最初から揃える。**  
実際の出走数（基本は 8プル）とは切り離して考える。

```yaml
creature_width: 0.8    # m
minimum_gap: 0.3       # m
# 1 体あたり必要幅 ≈ 1.1m
# 12 体横並び ≈ 13.2m 以上
```

| 項目         | 値   |
| ---------- | --- |
| **最小コース幅** | 14m |
| **推奨コース幅** | 16m |
| **最大コース幅** | 20m |

> **現行の実装との違い（2026/10/09時点）:** いまの体は、直径 **1.5 m** の円（当たり判定も見た目も。`M2TrackMath.BODY_DIAMETER_M`）、コース幅は **15 m**。上の `creature_width: 0.8` より大きいので、横に並べるのは、8体で12 m（幅に収まる）、12体では18 m（幅を超える）。12プルに対応するときは、体の大きさかコース幅を決め直す必要がある。

※ コースタイプの「広い／狭い」は、絶対幅ではなくカーブの鋭さ・直線比率の相対表現とする。  
※ 基本出走が 8プルでも、幅は 12プル分を確保する。集団密度は AI の位置取り（理想ラインへの寄り）などで調整する。

#### 🚪 スタートゲート

- **ゲート枠は最初から 12プル分の素材・配置を用意する**
- 8プルレースでは、そのうち使う枠だけ出走させる（未使用枠は空／閉など演出は実装時に決める）
- 使う・使わないはレース設定次第。作り直しを避けるため、ゲート資産は 12プル分で固定

### 🏇 出走数の方針

| 項目 | 内容 |
|------|------|
| **基本出走数** | **8プル** |
| **エンジン上限** | **最大 12プル**まで対応できる設計 |
| **β 版** | **8プル固定**でバランス・AI・観戦しやすさを優先調整 |
| **人数不足時** | 受付締切時点の空き枠を **CPU（NPC）で補充**し、常に 8プルにする |
| **コース幅・ゲート** | 最初から **12プル分**を用意（上記） |

> **現行（ローカルのオフラインフリー対戦、2026/10/08〜）:** レース選択画面で、2〜8プルを選んで走れる（ユーザー1＋CPU1〜7）。スタートの位置は枠番号どおりで、未選択の枠は空けたまま。脚質の「得意な順位」は、人数に合わせた式で決める（[`設定管理.md`](設定管理.md)）。

### 🎯 Godot の Path3D / Curve3D 採用理由

- ✅ 自然なコース形状に対応（円形・三角形・自由曲線など）
- ✅ オンライン同期が容易
- ✅ コース上の距離を進めるだけで位置決定できる

**実装方式:**

1. コース上の距離を進める
2. その地点の座標を取得
3. offset 分だけ左右へずらす

### 📏 カーブ率と内外ライン差（距離補正）

「ここはカーブ」と手動設定する方法もあるが、
**コース形状から自動計算する方式**を採用する。

- 🔄 コース形状に応じた自然な曲がり方
- 📐 円形・三角形・自由曲線などに対応可能
- 💻 オンライン同期が簡易的（距離を共有すれば OK）



#### 🌊 カーブ率（curve_strength）の計算

前方方向ベクトルと次方向ベクトルの角度差から求める。

```
curve_angle = angle(previous_direction, next_direction)

curve_strength = clamp(curve_angle / 90.0, 0.0, 1.0)
```


| curve_strength | 内容     |
| -------------- | ------ |
| 0.0            | 完全な直線  |
| 0.3            | ゆるいカーブ |
| 0.7            | 急カーブ   |
| 1.0            | ヘアピン   |




#### 📐 内外ライン差：距離倍率方式（distance_multiplier）

内外補正は **実効速度倍率ではなく、必要走行距離倍率** とする。

```yaml
line_bonus_type: distance_multiplier
```

意味：同じ対地速度でも、内側は短い中心線距離で済み、外側は余分に進む必要がある（競馬的で自然）。

**直線:** 曲率が無いので倍率は常に **100%**（内外で差を付けない）。

**カーブ（M2 実装・2026/08/26）:**

- 中心線の曲率 κ（≈1/R）から、幾何比 `(R + offset) / R` ＝ `1 + offset × κ` を基本にする  
  （見た目の流れる速さを内外で揃えやすい）
- 感触調整として **`GEOMETRIC_BLEND`（現状 0.85）** で 1.0 との間を取る  
  （完全な半径どおりより、内側有利・外側不利をやや抑える）
- コード正本: `client/scripts/m2_track_math.gd`（定数 `GEOMETRIC_BLEND`）

参考（コース中心半径 18m・可動端 offset ±6.75m・BLEND 0.85 のとき、端でおおよそ内側 **約 68%**／外側 **約 132%**）。数値は感触で変えてよい。

**弱い差の調整例（将来・curve_load と合わせて再検討してよい）:**


| ライン    | 距離倍率 |
| ------ | ---- |
| **内側** | 97%  |
| **中央** | 100% |
| **外側** | 103% |


カーブが強いほど差を広げてもよい（調整用の例）:


| カーブタイプ | 内側   | 中央   | 外側   |
| ------ | ---- | ---- | ---- |
| 直線     | 100% | 100% | 100% |
| 普通カーブ  | 97%  | 100% | 103% |
| 急カーブ   | 94%  | 100% | 106% |


※ 以前の表（内側 103% / 外側 97%）は距離倍率としては逆であり、採用しない。  
※ M2 は上表の弱い ±% ではなく、幾何＋BLEND を採用している（見た目速度優先のたたき）。

**現実の距離差の参考例:** 180 度カーブ、中心半径 20m・コース半幅 8m 程度なら、内外で走行距離に差が出る。ゲームでは現実値をそのまま使わず、上記のとおり調整する（内側が強すぎる／弱すぎるのを防ぐ）。

#### 🚦 カーブ負荷（curve_load）

内側が常に有利になる問題を防ぐため、
**「速度が高いほどカーブが難しくなる仕組み」**を入れる。

**初期実装（採用）:**

```
curve_load = speed × curve_strength
```

`speed² × curve_strength` は急激すぎる可能性があるため、初期は線形を採用する。

**将来の候補（必要なら）:**

```
curve_load = pow(speed, 1.5) × curve_strength
```

- **低速**: 問題なく曲がれる
- **高速**: 外側へ膨らむ、減速が必要



#### 🏃‍♂️ 旋回性能（コーナリング能力）

各生物に「旋回性能」または「コーナリング性能」を持たせる。

**判定例:**

```
必要旋回能力 > 生物の旋回性能の場合:
  ・外側へ膨らむ
  ・速度低下
  ・スタミナ消費増加
```



#### 📍 ライン選択の駆け引き

「内側が常に正解」ではなく、状況によってラインを選ぶ。


| ライン    | メリット              | デメリット                |
| ------ | ----------------- | -------------------- |
| **内側** | 走行距離が短い           | 曲がる難易度が高い / 前が詰まりやすい |
| **中央** | 安定                | 特になし                 |
| **外側** | 曲がりやすい / 追い抜きしやすい | 走行距離が長い              |


**状況に応じたライン選択例**


| 状況      | ライン  | 理由           |
| ------- | ---- | ------------ |
| **先頭**  | 内側   | 距離有利         |
| **後方**  | 外側   | 加速して追い抜く     |
| **集団中** | 中央付近 | ドラフティングで空力維持 |




#### 🔥 属性とコース適性の連携


| 属性    | 特徴                      | コース適性         |
| ----- | ----------------------- | ------------- |
| **地** | ・重心が低い ・カーブ安定 ・悪路に強い    | テクニカルコース / 山岳 |
| **水** | ・柔軟 ・旋回性能が高い ・内側ライン向き   | 雨 / コーナー重視コース |
| **火** | ・加速性能が高い ・直線向き ・急カーブは苦手 | 短距離 / 直線勝負    |
| **風** | ・最高速度が高い ・軽量 ・高速走行向き    | 高速コース / 長距離   |

## 🧱 接触・柵・コース形状の判定方針

オンライン・最大 12プル（基本 8プル）・`distance + offset` 方式のため、**Godot の物理 Collision をそのままゲームルールに使わない**。

### 大方針

| 対象 | ルール上の扱い | Godot 物理 Collision |
|------|----------------|----------------------|
| **他キャラ同士** | `distance` / `offset` の自前距離判定 | **使わない**（押し合い・反発しない） |
| **柵** | `offset` が左右限界に達した＝接触 | **ルールには使わない**（見た目用のみ可） |
| **地面** | 位置は Path 上の点＋offset で決定 | プロトタイプでは **不要寄り** |
| **カーブ／上り坂** | いまの `distance` から Curve3D を読んで計算 | 手動ゾーン配置は本判定に使わない |

キャラの最終位置は、物理結果を信じず **Path 上の点（distance）＋左右（offset）で上書き**する。

### 他キャラとの接触

横・縦の距離で判定する。

```
横: abs(offsetA - offsetB)
縦: abs(distanceA - distanceB)
```

例: 横 0.9m 以内かつ縦 0.8m 以内なら「接触中」。

接触後は完全停止ではなく、**目標 offset を少しずらして避ける**（例: 0m を目指していたが前に人がいれば +0.6m へ）。押し合いの強さは **接触耐性** などでゲームルールとして表現する。

#### 占有レーン（Reservation）

各ぷるりんが目指す `target_offset` が他キャラに占有されていれば、空いている隣へ少しずつ妥協する。

```
例: -2.5m が埋まっている → -1.8m → -1.2m
```

物理で押し合わなくても、集団走行・進路変更・ドラフティングと相性が良く、サーバーでも同じロジックを再現しやすい。

### 柵（コリジョンなしを基本）

**ルール上の柵は Collision ではない。**

```
offset が ±上限に達した
　＝ 柵に接触中
　＝ キャラ同士の接触と同系統の処理
```

| 処理 | 内容 |
|------|------|
| めり込み防止 | `offset` を上限でクランプ |
| ペナルティ例 | 減速、モチベーション低下など |
| 接触耐性 | 柵接触のキツさにも使える（任意） |

キャラ同士は相手が動くため押し合い・回避が必要だが、柵は動かない壁なので **クランプ＋ペナルティ** で足りる（完全同一コードである必要はない）。

#### 見た目の柵の置き方

手で 1000 個置く必要はない。

| 段階 | やり方 |
|------|--------|
| **プロトタイプ** | 柵メッシュなし。`offset` の上下限だけ |
| **見た目が必要** | **Path（Curve3D）に沿って左右へ自動生成** |
| **手置き** | ゲート・看板などスポットのみ |

Path からの生成イメージ:

```
distance を少しずつ進む
↓
その地点の左右へ ±コース半幅 ずらす
↓
柵メッシュを置く（または MultiMesh にまとめる）
```

見た目は柵モデルでよく、将来当たり判定を足す場合も **長い薄い箱（見えない壁）** を Path に沿って少数置く程度で足りる。見た目の柵メッシュそのもので細かい Collision を大量に持たない。

### 地面・高低差（坂）

高低差をまだ入れない段階では、**地面との物理接地は必須ではない**。

将来、中山競馬場のような坂を入れる場合も、地面物理ではなく **Curve3D 自体に高低差を入れる**方式を取る。

```
上り: 出力・心拍・スタミナ消費が増える等（任意）
下り: 巡航しやすい等（任意）
```

これは「地面に乗っている物理」ではなく、**コース形状パラメータとしての坂**。

### カーブ期間・上り坂の判定場所

手動で「ここからカーブ」「ここから上り」ゾーンを並べる方式は、本判定には使わない（Path とズレやすい／メンテが増える）。

**いまの `distance` から Curve3D を読んで都度計算する。**

| 知りたいこと | 出し方 |
|--------------|--------|
| カーブか／強さ | 前後の進行方向の角度差 → 既存の `curve_strength` |
| 上り／下り | 少し先の点と今の点の高さ差 → 勾配 |
| 直線か | `curve_strength` が十分小さい |

サーバー／クライアント／リプレイで、同じ Curve データと同じ `distance` があれば同じ結果になる。

手動ゾーンが向くのは、スタート・ゴール・特殊イベントなど **形から自動では分からない意味**がある地点だけ。

### 初期プロトタイプの構成まとめ

| 対象 | 実装方法 |
|------|----------|
| コース移動 | Path3D + `distance` / `offset` |
| 地面 | 物理接地なしで可（位置は Path で決定） |
| 柵（ルール） | `offset` クランプ＝接触。Collision なし |
| 柵（見た目） | 後回し可。必要なら Path 左右に自動生成 |
| 他キャラ | 物理 Collision なし。`distance` / `offset` 判定 |
| ドラフティング | `distance` / `offset` のみ |
| 接触・押し合い | 自前ロジック（接触耐性・位置関係） |
| カーブ／坂 | `distance` 地点の Curve 情報から計算 |

## 🏁 レース戦略・操作方式



### 📚 基本的なレース要素

- **能力**: 基本ステータス（最高速〜操作性）＋属性ボーナス
- **状態**: 残スタミナ / 心拍数 / モチベーション / ブースト状態
- **戦術**: 脚質 / 位置取り / ドラフティング / ブーストのタイミング
- **コース要因**: コース形状（直線・カーブ・ヘアピン）、距離カテゴリー

※ 気象風は扱わない。  
※ 脚質（逃げ・先行・差し・追込）の定義は「脚質システム」を参照。

### 🎮 操作方式（プレイヤー）

プレイヤーが直接操作する主操作は次のとおり。**現在速度は直接操作しない**（ローカルは出力ノッチ、M5 は目標スピードを指示し、ぷるりんが走る）。


| 操作 | 内容 |
| ---- | ---- |
| **左右移動** | 内外のライン取り（offset の指示） |
| **出力ノッチ／目標スピード** | 上下で操作。ローカルはノッチ（0〜6）とブレーキ、M5 は目標スピードの粗い刻み増減。自分でペースを作る |
| **ブースト発動** | 1 レース最大 3 回の仕掛け |


> **現行（ローカル、2026/10/09時点）のボタン:** レース中は、左右＝ライン、上下＝ノッチ、A／Space／左トリガー＝ブレーキ、B／Z＝ダッシュ、X＝ブースト、Y／C＝視点の切り替え、右スティック＝見回し、START／Esc＝一時停止。メニューは、A＝決定、B＝戻る、START＝レース開始、SELECT＝施錠、X＝選択解除、Y＝強制選択、L1・R1＝距離、L2・R2＝枠の移動。くわしくは [`設定管理.md`](設定管理.md)。

- **積極／温存などのペース帯プリセットはプレイヤー操作には使わない**（上下の出力操作に任せる）
- 内へ／外へ／スパート準備など、ペース以外の戦術指示を残すかは実装・UI を見ながら整理してよい

立ち位置は、ロードレースの監督に近い。指示を送るだけで、ぷるりんには乗らない。

```
プレイヤー: 状況判断 → ノッチ（目標スピード）・左右・ブースト
ぷるりん:   能力・脚質・状態 → 駆動と抵抗による速度変化・走行
```

### 📷 カメラ・視点・ミニマップ

レース中の情報把握は、**カメラ切替**と**ミニマップ**で行う。  
プレイ中・リプレイ・観戦で **同じカメラ／切替ロジック** を使い、いつでも切り替え可能とする。

#### カメラアングル

| アングル | 内容 | 備考 |
| ------ | ---- | ---- |
| **後方** | 対象ぷるりんの後ろから追従 | **デフォルト** |
| **前方** | 対象の前から見る | |
| **横** | 対象の横から見る | |
| **頭上やや後方** | 斜め上から俯瞰気味に追従 | 本番候補 |
| **真上俯瞰** | 真上から見下ろす（正射影可） | **M2 たたき**で速度感確認用。C キー切替 |

> **現行（ローカルレース、2026/10/07〜）:** 視点は4つ（デフォルト＝後ろ6m・高さ3m、遠距離＝後ろ12m・高さ4m、上空＝高さ40m、一人称＝自分の体を隠す）と、右スティックの見回し。カメラの対象は自分だけで、ほかのぷるりんへの付け替え・前方や横からの視点・ミニマップは、まだ無い。そのため、レース中の顔（表情）は、今の視点ではほとんど見えない。

※ M2 試作（`camera_m2.gd`）は **後方追従** と **真上＋正射影** の2種。斜め俯瞰は遠近で速度が分かりにくかったため採用していない。本番の「頭上やや後方」は後で差し替えてよい。

#### カメラ対象

- デフォルトの対象は **自分の操作ぷるりん**
- **他のぷるりん**にもカメラを付け替え可能（自分専用視点に固定しない）
- 対象の切替は、後述のミニマップ／前後スライド選択と連携する

#### カーブ時のカメラ挙動（保留）

カーブでカメラを外側へ振るかどうかは **未確定**。

- 開発が進んでから実機テストで判断する
- または設定画面で ON/OFF できるオプションにする

初期実装では **ほぼ真後ろ固定** で進め、挙動は後から差し替えやすい形にしておく。

#### ミニマップ・個体選択

後方カメラだけでは見えにくい「後方の相手」や「集団全体」は、ミニマップと UI で補う。


| 要素 | 内容 |
| ---- | ---- |
| **ミニマップ** | 集団全体の位置関係を表示。倍率変更・前後スクロールが可能 |
| **前後スライド選択** | 特定キーで前後のぷるりんを順に選択 |
| **選択時の利用** | 選択中ぷるりんのステータス情報表示、およびその個体へのカメラ切替 |


※ キー割り当て・UI 配置の詳細は実装時に決める。方針として「集団把握＝ミニマップ」「個体注目＝スライド選択＋カメラ」とする。

| **trainer profile** | `line_pref`（内寄り志向、0〜1）だけを使う。個体は roster の `trainer_profile_id` で参照する |
| **脚質・属性** | CPUの判断には使わない。順位・区間に応じた有効ステータス補正（速度・心拍・スタミナ等）としてだけ効く |
| **作り直し** | 2026/10/08 に、1から作り直すと決めた（検討事項「オフラインフリー対戦とCPUトレーナーの作り直し」）。今ある処理の洗い出しまで済み、残す・消すの判断待ち |
| **ブースト・ダッシュ** | プレイヤーだけ実装済み（2026-10-06）。CPUは使わない |

つまり現行CPUは「同じノッチで走り、心拍が危なくなったら緩める。ラインだけは状況を見て選ぶ」という最小構成である。個体差は、ステータス配分・属性・脚質・ライン志向から出る。



### 🎯 位置づけ

ジャンル感としては、

**競馬ゲーム ＋ 自転車ロードレース戦術** の中間。

マリオカート型のアイテム・直接ドリフト操作レースではない。

プレイヤーは **トレーナー** として作戦と指示を出す。ぷるりんには乗らない。  
実際に走るのは **ぷるりん**。

```
プレイヤー（トレーナー）
    ↓ 作戦・指示
ぷるりん（能力・脚質に基づき走行）
```

同じ能力のぷるりんでも、トレーナーの作戦・指示が違えば走りが変わる。  
負けたときに「運が悪かった」ではなく、「作戦ミス／配分ミス」と感じられることを目指す。

### ❌ この章で採用しないもの

余計な運要素とみなして、**採用しない**。


| 非採用                             | 理由                 |
| ------------------------------- | ------------------ |
| ぷるりんの従順度                        | 指示無視が乱数化しやすい       |
| トレーナースキル（補正付きパッシブ等）             | 収集・ガチャ寄りになりやすい     |
| mistake / reaction_error などの揺らぎ | 完全再現防止のための「擬似運」になる |


NPC に「最適ライン・最適加速を知る正解 AI」も与えない。  
判断は脚質・性格パラメータ・状況ルールに基づくが、**最適解を計算して常に正解を取る AI にはしない**。

### 🧩 役割分離

```python
class Pururin:

    running_style  # 逃げ / 先行 / 差し / 追込

    patience        # 温存・我慢
    drafting_pref   # 集団・ドラフト志向

```

| ---- | -------- |
| **Trainer（プレイヤー）** | ノッチ（M5 は目標スピード）、左右、ブースト、（任意の）戦術指示 |
| **Trainer（CPU）** | *（将来構想）* 目標順位帯、積極／温存などのペース方針、内外・スパート方針 → 出力へ落とし込む。現行は上の表の最小構成 |
| **Pururin** | 能力と脚質に従い、`target_offset` / `target_speed` へ実際に動く |

| 種別 | プレイヤー | CPU（NPC） |
| ---- | -------- | -------- |

### 🏆 最終的な勝敗要素

勝敗は以下で決まる。

1. **能力配分**
2. **属性**
3. **脚質**
4. **トレーナー判断**（作戦・性格パラメータ）
5. **レース中判断**（指示）
6. **ブースト使用タイミング**
7. **位置取り**

運ではなく、**「いつ仕掛けるか」「どこで我慢するか」「誰の後ろにつくか」**が重要になる。

### 🤖 NPC AI の基本方式（将来構想）

> 以下は未実装の構想。現行CPUとの差は章冒頭の表を参照。

NPC（他トレーナー）も、キャラを直接スティック操作するのではなく、

```
目標を決める → そこへ向かう
```

方式とする。

**トレーナー AI（方針決定）の優先度例:**

```
priority 1: 勝負位置へ移動
priority 2: スタミナ温存
priority 3: ブースト判断
```

**ぷるりん AI（実行）:**

```
現在状態を判断 → 指示を解釈 → 走行
```



#### 3 層構造

```
戦略 AI（数秒〜1 秒単位）
    ↓
行動 AI（おおよそ 0.2 秒）
    ↓
操舵 AI（毎フレーム）
```


| 層         | 更新頻度の目安    | 内容                              |
| --------- | ---------- | ------------------------------- |
| **戦略 AI** | 約 1 秒に 1 回 | 先頭へ行くか／集団に残るか／スタミナ温存か／追い込み開始か   |
| **行動 AI** | 約 0.2 秒    | 内へ／外へ／加速／減速などの具体行動              |
| **操舵 AI** | 毎フレーム      | `offset` / `target_speed` へ近づける |


**処理の流れ:**

```
npc.update()
  → decide_strategy()
  → decide_target_position()
  → decide_target_offset()
  → speed_control()
```

**戦略 AI の例（概念）:**

- スタミナが低い・心拍が高い → 温存
- 終盤 → 攻撃（仕掛け）・ブースト判断
- 空気抵抗が大きい状況 → ドラフト位置を優先

**行動 AI の例（概念）:**

- 前が詰まった → 外へ出す
- 急カーブ → 速度を落とす

**ライン取りの例（属性・方針との連携）:**

- 水寄り・内重視 → カーブ前に内へ
- 火寄り・直線重視 → 外へ出して加速

（実装時は属性・`corner_pref`・指示の組み合わせで決める）

**スタミナ管理（必須寄り）:**

現在スタミナ・残り距離・順位を見て、

- まだ遠い → 温存
- 残りわずか（例: 300m）→ 全力



### 🪜 初期実装のおすすめ範囲

まずは次だけで「生き物がレースしている感」を出す。

- 脚質
- トレーナー性格パラメータ（aggression 等）
- 簡単な位置取り（目標順位 → offset / speed）

トレーナースキルツリー、従順度、意図的ミス率は入れない。

**実装状況（2026/10/03）:** 位置取りのうちラインの選択（offset）は実装済み。脚質・性格パラメータによるペース判断は、一度実装した（`aggression` / `patience` / `drafting_pref` による目標速度補正）が、ノッチ方式への移行と燃料タンク化に合わせて削除した。再導入するときは、ノッチと心拍・燃料の仕組みの上で設計し直す。

#### 🎬 モーション設計

> **現行（2026/10/09）:** 体全体と、頭の上・左右・尾の部品が、アクションごとに動く。体全体は、待つ＝ゆっくり呼吸、スタート前＝縮んで構える（スタートで前へ伸びる）、走る＝小さく跳ねる、ダッシュ＝前後に伸びる、ブレーキ＝後ろへ反る、接触・押し合い＝横につぶれる・震える、疲れた＝へたる、1位でゴール＝跳ね回る、2・3位＝小さく跳ねる。横へ動くとき・カーブでは、体を傾ける。動きの大きさと速さは、個体ごとに変えられる（地は重く、風は軽い）。動きは見た目だけで、当たり判定・順位・タイムには関係しない。

リアルな動物より、架空生物らしい動きを重視。

- **スライム系**: 伸びる / 縮む / 跳ねる
- **パワー型**: 大きく踏み込む / 地面を揺らす
- **高速型**: 体を流線型に変形する

---

### 🎭 見た目カスタム（体は設定から組み立てる。部品は取り替えられる）

方針（2026/10/08に変更）: 体は、**設定ファイルから、プログラムで形を作って組み立てる**。部品（体・頭の上・左右・尾・目・まゆ・口・ほっぺ・マーク・体に巻く絵）は、1つずつ、自分で用意したメッシュ（`.glb`）や画像（`.png`）に取り替えられる。

以前の方針「3D モデルは共通／差は画像で表現」は、色ちがいの球にしか見えず、個体の見分けが付きにくかったので、やめた。

※ 見た目は、**能力値や勝敗に影響しない**（能力はポイント配分で決める方針と分離）。

#### 決まり

| 項目 | 内容 |
|------|------|
| **体の横幅** | 全員同じ（一番太い所が半径 0.75 m＝当たり判定と同じ）。細い体・太い体は作らない（当たり判定と見た目がずれるため） |
| **個体の差** | 体の高さ、頭の上・左右・尾の部品、色、顔、マークで出す |
| **飾りと当たり判定** | 頭の上・左右・尾の部品は、当たり判定に入れない（横に並ぶと、隣の体に少し刺さって見えることがある） |
| **設定の誤り** | 知らない部品・無いファイル・書き間違いは、別の形に替えずに、読み込みを止める |

#### 部品の3種類

| 種類 | 例 | 変わり方 |
|------|----|----------|
| **体の一部** | 水＝突起とヒレ、地＝岩、火＝炎、風＝芽と葉の羽 | アクション（待つ・構える・走る・ダッシュ・ブレーキ・接触・押し合い・疲れ・ゴール3種類）ごとに動く。岩は動かない |
| **顔** | 目、まゆ、口、ほっぺ、効果（汗・涙・キラキラ・怒りのマーク） | 表情ごとに入れ替える |
| **飾り・マーク** | 星、ハート、しずく、いなずま、花、ひし形、三日月、うずまき | 変わらない |

体の質感は、属性ごとに変える（水＝つや、地＝つや消しでざらざら、火＝内側から光る、風＝ふちが白く光る）。

#### 色

- 体の色（第一カラー）は、属性ごとの選択肢（4色ずつ）から選ぶ。ふちの線の色も、一緒に決まる。
- 第二カラーは、体の下のほう（高さは個体ごと）に塗る。体の本体だけに塗り、部品には塗らない。
- 操作盤・順位表・着順の板の丸も、体と同じ色を使う。

#### 表情

表情は8つ。あとから足せる。個体ごとに、別の顔のひとそろいを持つ（今の8体は、全員ちがう）。

| 表情 | レース中のきっかけ（上ほど優先） |
|------|------|
| 1位 | 1位でゴール |
| 喜 | 2位・3位でゴール |
| 押し合いで負けた | 押し合い中で、接触耐性で負けて押し出されている |
| 押し合いで頑張る | 押し合い中で、負けていない |
| 怒 | 横で接触している |
| 哀 | 体力がマイナス、または心拍が通常上限ごえ |
| 楽（ほっこり） | ドラフトで楽をしている |
| ノーマル | それ以外 |

- ノーマルは、必ず用意する。ある表情の顔の部品が無いときは、ノーマルを出す。
- レース選択画面では、選んでいる個体の体がゆっくり回り、1回転ごとに表情が替わる。

#### まだ無いもの

- 色・部品・マークを、ゲームの中の画面で選ぶ機能（今は、設定ファイルで決める）。
- 頭の上・左右・尾の部品の、属性ごとの種類ちがい（今は、属性ごとに1種類ずつ）。

設定の項目と、取り替え用の素材の決まりは、[`設定管理.md`](設定管理.md) の「ぷるりんの見た目」。

### 🖥️ サーバー構成案（1 サーバーでの複数レース同時開催）



#### アーキテクチャ概要

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────┐
│   プレイヤー │ UDP │  ゲームサーバー   │ WebSocket │ データベース
│    (Godot)  │ ←→  │  (Python asyncio) │ ←→    │  (SQLite)  │
└─────────────┘     └────────┬─────────┘     └─────────────┘
                             │
                    ┌────────▼────────┐
                    │ GameServer      │
                    │ ├ LoginManager  │
                    │ ├ MatchMaking   │
                    │ └ RaceManager   │
                    │    ├ Race#1001  │
                    │    ├ Race#1002  │
                    │    └ Race#1003  │
                    └─────────────────┘
```



#### 🔑 設計原則：1 レース = 1 管理単位

全レースを 1 つの巨大ループで回すと、重いレースが他レースまで遅延させる。  
そのため **Race ごとに独立**させ、asyncio では **1 レース = 1 Task** とする。

```
GameServer
│
├ RaceManager
│   ├ Race#1001  → asyncio Task（race_loop）
│   ├ Race#1002  → asyncio Task（race_loop）
│   └ Race#1003  → asyncio Task（race_loop）
│
├ MatchMaking
├ LoginManager
└ Database
```

**データ構造のイメージ:**

```python
class Race:
    race_id: int
    players: list
    state: str
    def tick(self):
        ...

class RaceManager:
    races: dict[int, Race]  # {1001: Race(), 1002: Race(), ...}
```

- プレイヤーは `player.race_id` だけ持つ
- 受信パケットは `races[player.race_id]` へ流すだけ
- 各レースはおおよそ 50ms（20Hz）ごとに独立して `tick()` する

**メリット:**


| 観点       | 効果                        |
| -------- | ------------------------- |
| **負荷分離** | 満員レースが重くても、他レースへの影響を抑えやすい |
| **障害隔離** | 1 レースのバグで全サーバー落ちになりにくい    |
| **将来拡張** | レース単位で別 VPS へシャーディングしやすい  |


**β では不要だが最初から入れておくこと:**

- `Race.tick()` を独立させる
- `RaceManager` 経由でのみレースを管理する

β は「1 VPS + RaceManager + 同時 5〜10 レース」で十分。構造だけ先に分離しておくと、後から 1 台 → 2 台 → 10 台へ拡張しやすい。

#### 📈 将来の拡張（シャーディング）

人気が出て同時レース数が増えた場合の分割イメージ:

```
ServerA: Race1〜50
ServerB: Race51〜100
```

さらに進めると:

```
Login Server
    ↓
Lobby Server
    ↓
Race Server 1 / Race Server 2 / Race Server 3
```

ロビーが空きのある Race Server へプレイヤーを振り分ける。

#### 📊 通信量の概算（20Hz）

前提: 1プルあたり送信情報は `id / distance / offset / speed / 状態フラグ` 程度。圧縮後おおよそ 32 byte。

| 項目 | 8プル（基本） | 12プル（上限） |
|------|-------------|--------------|
| 1 回の送信 | 約 256 byte | 約 384 byte |
| 1 クライアント向け | 約 5 KB/s | 約 7.5 KB/s |
| 全員へ配信（1 レース） | 約 40 KB/s | 約 90 KB/s |

帯域（例: 100Mbps 共有）はボトルネックになりにくい。問題になりやすいのは **CPU**（ドラフティング判定・簡易衝突・順位計算など）。基本 8プルの方がサーバー負荷は軽い。

#### 🧮 さくら VPS 2GB（3vCPU）での同時開催目安

| 条件 | 同時レース目安 | 人数目安（基本 8プル） | 人数目安（12プル時） |
|------|----------------|---------------------|-------------------|
| **軽い実装**（物理なし・サーバー AI なし・当たり判定簡易） | 20〜50 レースの可能性 | — | — |
| **現実的な安全圏**（Python asyncio + SQLite + ログ + Web 管理） | **5〜10 レース** | **約 40〜80 人** | **約 60〜120 人** |
| **Phase1〜β の運用目標** | **同時 5 レース前後** | **約 40 人程度** | — |
| **正式版の目標レンジ** | **同時 10〜20 レース** | **約 80〜160 人程度** | **約 120〜240 人程度** |


**スケール方針:**

- 開発初期〜β: さくら VPS **2GB で十分**（最初は余る想定）
- 同時 100 人を超えてきたら **4GB へスケールアップ**を検討

**2GB が厳しくなりやすい要因（サーバー側に載せ始めた場合）:**

- サーバー側 AI / NPC 思考
- 本格的な物理判定・集団押し合い
- リプレイ保存 / 毎 tick 保存
- Discord 連携・重いレーティング計算など



#### 📊 レース管理設計（運用パラメータ）

- **同時開催数**: β は **5〜10 レース**を安全圏とする（初期検証は 2〜4 からでも可）
- **各レースの独立性**: 位置データは完全に分離、干渉なし（1 レース = 1 Task）
- **通信負荷最適化**:
  - 1 レースあたり 20〜30ms 間隔（おおよそ 20Hz 前後）で位置更新
  - プレイヤーは参加しているレースのみを受信

### 🎬 リプレイシステム

`distance + offset` 方式のため、リプレイとの相性が良い。再生時は記録した値をそのまま適用すれば、同じレースを再現できる。

#### 採用方針


| 方式                | 内容                     | 方針                                   |
| ----------------- | ---------------------- | ------------------------------------ |
| **方法1: 状態記録（基本）** | 一定間隔で各生物の状態を保存し、再生時に適用 | **採用**                               |
| **方法2: 入力のみ保存**   | 操作入力だけ保存し、再シミュレーション    | **非推奨**（ドラフティング・乱数・AI が増えると完全再現が難しい） |
| **方法3: イベント＋補間**  | 例: 1 秒ごとに完全状態、その間は補間   | 容量削減オプションとして将来検討可                    |




#### 記録内容（方法1）

おおよそ 20Hz（50ms ごと）で保存する例:

```
時刻 0.00 秒
  Player1: distance=0.0,  offset=0.2,  speed=12.1
  Player2: distance=0.0,  offset=-1.1, speed=11.8

時刻 0.05 秒
  Player1: distance=0.6,  offset=0.3,  speed=12.0
  Player2: distance=0.58, offset=-1.0, speed=11.7
```

最低限でも `distance` / `offset` があればかなり再現できる。必要に応じて以下を追加する。

- speed / stamina
- animation_state / スキル発動
- 順位などメタ情報

**フレーム構造イメージ:**

```python
ReplayFrame:
    timestamp
    players:
        id
        distance
        offset
        speed
        stamina  # 任意
```



#### データ量の概算（12プル・20Hz）


| 項目                                          | 概算       |
| ------------------------------------------- | -------- |
| 1プルあたり（distance / offset / speed 各 float32） | 12 byte  |
| 1 フレーム（12プル）                                | 144 byte |
| 1 秒                                         | 約 2.9 KB |
| 5 分レース（300 秒・上限）                            | 約 0.9 MB |


スキル・順位・スタミナなどを足しても、**1 レース数 MB 程度**を想定。

#### 保存形式例

```json
{
  "version": 1,
  "course": "oval01",
  "frames": [
    {
      "time": 0.0,
      "players": [
        { "id": 1, "distance": 0.0, "offset": 0.1 }
      ]
    }
  ]
}
```



#### 保存・保持方針（現時点）

- **全レースのリプレイデータを保存する**
- **保持期間は 14 日**。期限切れは自動削除する
- 大会・ランキング入りなどの「永久保存」例外は、現時点では設けない（必要になったら別途検討）

SSD 容量は 1 レース数 MB 規模なら、14 日ローテーションでも現実的な範囲に収まりやすい。

#### 再生・演出（将来）

記録データを適用するだけで再生できるため、カメラや演出にも転用しやすい。

- **カメラ**: プレイ中と同じ切替（後方デフォルト／前・横・頭上やや後方、他ぷるりんへの付け替え）。M2 たたきでは後方＋真上正射影。詳細は「カメラ・視点・ミニマップ」を参照
- ゴール前スロー
- ベストレースの再視聴

※ **観戦モード**とリプレイは内部的に近い仕組みになる想定。観戦を入れるならリプレイ基盤がほぼ必須。  
※ 観戦・リプレイでも、プレイ中と同様にアングル／対象／ミニマップ操作をいつでも使える。
