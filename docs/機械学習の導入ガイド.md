# ゲームのCPUに機械学習（強化学習）を入れる手引き

ぷるりんレーサーズで、レースのCPUを強化学習で育てたときのやり方と、うまくいった点・失敗した点をまとめたもの。
**別のアプリ（別のゲーム）に同じことをするエージェントが、最初に読む**ために書いた。実物は `lab/rl/`（Godot＋Python）。

---

## 1. 何をしたか（ひとことで）

- 人が決めるのは「CPUが何を見るか」と「何が良い結果か（点）」だけ。走り方（操作）は、CPUが何万レースも自分で走って見つける。Gran Turismo の「Sophy」と同じ考え方。
- ゲームはそのまま使い、画面なし・早回しで何本も同時に走らせる。学習は Python（PyTorch ＋ stable-baselines3 の PPO）。ゲームと Python は、同じPCの中の通信（TCP、1行に1つの JSON）でつなぐ。
- 人（ユーザー）が遊んだ記録を「お手本」として自動で取り込み、人らしさを残しつつ強くした。
- 結果：数時間で、ゲームの手作りCPUより明らかに強くなった。ゲームの決まりのすき（スタート直後のブースト3連発）まで見つけた。

## 2. 先に知っておくこと（いちばん大事）

1. **手作りの「つまみ」を育てるやり方は、うまくいかなかった。** 人が「気持ち」や「重さ」の項目を決め、その数字を CMA-ES などで育てる方法は、5代育てても強くなったかはっきりしなかった。人が決めた項目の外の走りは出てこないため。→ 最初から強化学習にする。
2. **強化学習は、点が上がるなら何でもやる。** 人なら「ずるい」「つまらない」と避ける作戦も見つける。変な勝ち方は、ゲームの決まりのすきの知らせとして扱い、直すかどうかは人（ユーザー）が決める。CPUの頭に「この場面ではこうするな」という特別なルールは入れない。
3. **入れてよい決まりは、ゲームの決まりだけ。** 「ブーストは3回まで」のように、ゲームが受け付けない操作は、選べなくする（使えない操作を外す仕組み＝アクションマスク）。それ以外の場面ごとの例外・固定の間隔などは入れない。
4. **点は、良い・悪いが決まったその場で渡す。** 頭が見るのは「今の様子」だけで、それまでに何をしたかは覚えていない。「ラスト25%で押したブーストに点」をゴールでまとめて渡したら、押した判断まで届かず、何時間育てても早押しが直らなかった（本番3）。行動の点は押したその時、続けている間の点（脚質の位置・風よけ）は進むたびに少しずつ、線を越えた時の点（体力）は越えたその時に渡す。ゴールで渡すのは、着順などレースの結果だけ。点を決めたら、点ごとに「いつ渡すか・そのとき頭に何が見えているか」の表を作って確かめる（Gran Turismo の Sophy も、点は全部0.1秒ごとにその場で渡している）。
5. **言葉のAI（ChatGPT など）はゲームのCPUには向かない。** 遅い・高い・細かい数値の操作が苦手。ゲームの中で0.5秒ごとに動く係は、強化学習で育てた小さな頭（数字の表）。

## 3. 進め方（この順で）

### 手順0：ユーザーと決める・準備する
- ゲームの「何を操作するか」「何を見せてよいか（人に見えている情報か）」「何が勝ちか」を、ユーザーに聞いて決める。人の画面やメニューで公開されている情報（順位表・パドックの能力など）は、全部見せてよい。
- **入れるもの**（Python の仮の箱＝venv、PyTorch、stable-baselines3、sb3-contrib、gymnasium、numpy）は、何をどこへ・どのくらいの大きさかを書いて、ユーザーの確認を取ってから入れる。PyTorch のグラフィックボード版は合わせて約6〜7GB。
- **ディスクの空きを先に見る。** 今回は「/」の空きが4GBしかなく、venv も pip のキャッシュ（`PIP_CACHE_DIR`）も一時置き場（`TMPDIR`）も、別のドライブに置いた。
- ゲーム本体のファイルは、ゲームに取り込むと決めるまで変えない。ラボ（学習の道具）は、ゲームの書き出しに入らない場所（リポジトリ直下の `lab/` など）に置く。

### 手順1：速さを測る
- まず、ゲームのレース（1試合）を画面なし・早回しで回して、何倍速で回るか、何本同時に回せるかを測る。これで育つ速さの見込みが決まる。
  - Godot なら `--headless --fixed-fps 30`（実時間に合わせず、1コマ1/30秒で回せるだけ回す）。今回は1本で実時間の約13倍、8本同時で2000mのレースが1分に約19本。
- 時間の流れが、1コマの長さ（delta）だけで決まるか（画面の速さに左右されないか）を確かめる。

### 手順2：つなぎを作る（ゲーム ⇄ Python）
- ゲーム側：レースを1本ずつ走らせる小さな起動の台本（`lab/rl/rl_worker.gd`）。決めた間隔（0.5秒）ごとに、
  - 送る：見たもの（数字の並び）・点・終わったか・選べる操作の印
  - 受け取る：操作 → ゲームの「人が操作する入口」に入れる（オンラインで人が使うのと同じ入口。CPUだけ有利な入口を作らない）
  - 返事を待つあいだ、ゲームの時間は止める（学習側が遅くても、ずれない）
- Python 側：ゲームを何本も起動し、全部の席をまとめて1つの学習の場（VecEnv）として扱う（`lab/rl/godot_env.py`）。1レースの8席全部を学ぶ席にすると、1本で8倍学べる。
- 同じくじの番号（seed）なら同じレースになるようにする。学ぶレースと比べるレースの番号は分ける。
- 確かめの道具（`lab/rl/check.py`）：見たものの並びの長さが毎回同じか、選べない操作が外れているか、同じ番号で同じ結果か。

### 手順3：見るもの・操作・点を決める（設定ファイルに置く）
- **見るもの**：自分の状態（速さ・体力・心拍・残りの切り札・位置など）、自分の能力と性格、ほかの全員の同じ値（順位の順に並べる）、レース全体の流れ（先頭の速さ・隊列の長さなど）、コースの先の形、残り距離の割合。値は −1〜1 くらいにそろえる（決めた上限で割る）。「いない」「遠すぎる」は上限の数字に置きかえる。
- **操作**：少数の選択肢に分ける（例：ノッチ下げる・そのまま・上げる、ライン内・そのまま・外、ブレーキ・ダッシュ・ブーストの押す・押さない）。使えない操作は外す（MaskablePPO）。
- **点**（`rl_settings.json` の `reward`）：
  - ゴールの着順の点がいちばん大きい（1位を特に大きく）。
  - 1位でなかったときは、1位とのタイム差が小さいほど少し足す。ただし「2位の点＋この分」が「1位の点」を超えないこと。
  - 前へ進んだ分の小さな点を毎回足す（何もしなくても学びが進むように）。
  - 性格（脚質など）に合った走りの点は、着順の点のいちばん小さい差より小さくする。中身はユーザーに見せて確認を取る。
  - 着順以外の点は、その場で渡す（2. の4）。
- 点の重さや項目は、全部設定ファイルに置き、あとから変えられるようにする（目標を変えたら、今の頭から続きを学び直せばよい）。

### 手順4：お手本（人の記録）を入れる
- ユーザーは「ふつうに遊ぶだけ」でよい作りにする。ゲームがもともと残す記録（今回は0.5秒ごとの状態の記録）を、ラボが自分で見つけて、お手本の束に足す。途中でやめたレース・こわれた記録は、自動で外す。
- 使い方は2つ。
  1. 学び始めに、お手本をまねさせる（でたらめな頭から始めずに済む）。
  2. 学びの途中でも、お手本に少しだけ寄せ続ける（はじめ強め、だんだん弱める）。人らしさが残る。寄せすぎると人より強くなれない。
- お手本は使い捨てにせず、取っておいて、頭を直すたびに見直す。結果の良かったレースほど少し重く見る。
- **記録が少ないうちは、まねを強くしない。** 6本だけで強くまねさせたら、ダッシュやブーストを何十回も押す変な癖がついた。目安：全部の距離を合わせて数本なら軽く、数十本ではっきり、100本以上でかなり再現。1つの頭が距離を見て走り分けるので、距離ごとに分けずに合わせて使う。

### 手順5：育てる・相手を混ぜる・確かめる
- 学び方は PPO（sb3-contrib の MaskablePPO）。頭の大きさは2段×256で足りた。
- 進み具合は、決まった本数ごとに表（CSV）へ書き、ユーザーに読み方を説明する（1位のタイム、ゴールしなかった割合、ダッシュ・ブーストの回数、残り体力、性格に合った割合、お手本と合う見込み）。
- 自分どうしだけで走らせると、同じ相手にだけ強くなる。**「控え室」**（`lab/rl/pool.py`）：前の版や、別の目標で育てた頭を置き、1レースのうち数席をそこからくじで選んで走らせる（学ばない）。
- 目標の違う頭を並べて育てられる（例：勝ちだけ／性格重視／人の分身）。設定の上書きファイル（`override_*.json`）で、その頭だけ点の重さを変える。
- 確かめ：まだ使っていないくじの番号のレースで、手作りのCPUや前の版と走り比べる。変な勝ち方をしていないか、画面ありで再生して、ユーザーに見てもらう。
- ユーザーが一緒に走れる道具（`lab/rl/play.py`）を作ると、実感がつかめて話が早い。ゲームの出走表の「スタート」だけをラボのレースにすり替える小さな入口（`RaceSession.race_starter`）をゲームに足した。ふつうに遊ぶときは何も変わらない。
- 人と同じ条件にするため、CPUの操作が届くまでに遅れ（今回0.3秒）を入れた。

### 手順6：ゲームに取り込む（ユーザーの「よし」のあと）
- 頭の中身（数字の表：入力の並び・大きさをそろえる値・各段の重み・出力の並び）を JSON に書き出す。
- ゲームの言語（GDScript など）で、同じ計算（掛けて足して、を数段）をする小さな部品を作り、決まった入力で Python と同じ答えになるかを確かめる。PyTorch はゲームには入れない。
- 席の動かし方は、ラボと同じ「人が操作する入口」を使う形にすると、オフラインでもオンラインのサーバーでも同じ頭がそのまま使える。

## 4. 起きた失敗と、その手当て

| 起きたこと | 手当て |
|---|---|
| 手作りの「つまみ」を育てても強くならない | 強化学習に切り替えた |
| 少ない記録のまねで、変な癖（連打）がつく | 記録の本数に応じて、寄せる強さを変える |
| CPUがスタート直後にブーストを3回使い、人が全く勝てない | ゲームの決まりのすき。同じ条件で使い方だけ変えて走らせ比べ（9本中9本1位 vs 3本）、原因を数字で示した。直すかはユーザーが決める |
| 「重ね押しの割り増しが原因」という説明が、実は違った | 思い込みで説明せず、使い方だけ変えた走らせ比べで確かめる |
| ディスクがいっぱいになりかけた | venv・キャッシュ・一時置き場を、空きのあるドライブへ |
| ゲームの仕様を変えたら（ノッチ0の廃止）、ブレーキ中に体力が減るようになった | 仕様を変えたら、テストを全部流す。テストの期待値は、設定と式から作る |
| 「ラスト25%で押したブースト」に点を付けたのに、早押しが直らない（体力も使い切る） | 点をゴールでまとめて渡していたのが原因。頭は今の様子しか見ないので、どの判断の点か分からない。その場で渡すように直した。育てながら狙いの数字（押した位置・線での体力）を測り、逆へ動いたら止める |
| 学習中の重さで、画面のテストが時々落ちる | テストを流すときは、育成を軽く（`--games` を減らす、`nice`）するか、落ちたものを流し直して確かめる |

## 5. ユーザーとの進め方（今回のユーザーの決まり）

- 結論を先に、短く、普通の言葉で。専門用語は言い換える。数字は表にする。
- 入れるもの・ゲームの設定の変更・ゲームへの取り込みは、必ず先に確認を取る。
- 少しやってから報告する。どんな形のデータで、どう確かめたかを見せる。勝手に変な設定を決めない。
- ユーザーの一言に合わせて、自分のおすすめをすぐ翻さない。違うなら違うと、理由を添えて言う。
- 決めたことは下書き扱い。あとの指示が優先。

## 6. ファイルの組み方（今回の形。別のアプリでもこの分け方でよい）

| ファイル | 役目 |
|---|---|
| `rl_settings.json` | 点の重さ・見るものの大きさをそろえる値・くじの番号・学び方の数字・お手本・控え室（全部ここ。すべて仮） |
| `override_*.json` | 目標の違う頭だけの、設定の上書き |
| `client/scripts/cpu_brain/brain_observe.gd` | 見るもの（数字の並び）と、選べる操作の印（ゲームの中のCPUと同じものを使う） |
| `rl_race.gd` / `rl_worker.gd` / `rl_link.gd` | ゲーム側：レース1本を走らせて、Python とやりとり |
| `godot_env.py` | Python 側：ゲームを何本も起動し、席をまとめて学習の場にする |
| `train.py` | 育てる（続きから・名前を付けて・同時に動かす数を指定） |
| `demos.py` / `rl_demos.gd` | お手本（人の記録）を見つけて、場面と操作の組にする |
| `pool.py` | 控え室（相手役の頭） |
| `play.py` | 人が一緒に走る |
| `check.py` | つなぎの確かめ |
| `runs/<名前>/` | 育てた頭（`latest.zip`・決まった間隔ごとの版）と進み具合の表（git に入れない） |

```bash
# 育てる（PCを軽くするなら nice と --games 4）
nice -n 19 <venv>/bin/python lab/rl/train.py --name 育成1 --games 4
# 続きから
<venv>/bin/python lab/rl/train.py --name 育成1 --resume lab/rl/runs/育成1/latest.zip
# 一緒に走る
<venv>/bin/python lab/rl/play.py
```

## 7. 別のゲーム・別のエンジンに移すとき

- 考え方（見るもの・操作・点・使えない操作を外す・お手本・控え室・同じ条件での比べ）は、そのまま使える。
- 要るのは3つだけ：①画面なし・早回しで1試合を回す方法、②決めた間隔で「見たもの・点・終わったか・選べる操作」を外へ出し、操作を受け取る入口、③同じくじの番号で同じ試合になること。
- Unity なら公式の ML-Agents、Godot なら godot_rl_agents もあるが、ゲームのプロジェクトに部品を混ぜたくないなら、今回のように小さなつなぎを自分で作るほうが扱いやすい（ゲーム側100行ほど、Python 側200行ほど）。
- ブラウザのゲーム（JavaScript）なら、頭の計算は数段の掛け算と足し算なので、書き出した JSON をそのまま読んで動かせる。
