# 設定管理と共通化

## 今回の対象

ローカルレースの出力操作に関する調整値を JSON に分離し、M5 の両側で同じ意味を持つドラフト規則と、ローカル／オンラインのゴール演出を共通化する。ローカルのノッチと抵抗のバランスは検討事項 #28 を正とする。

- ローカル走行設定の正本: `client/data/config/local_race.json`
- 読み込み・検証: `client/scripts/config/local_race_config.gd`
- M5 ドラフト規則の正本: `shared/m5_draft_rules.json`
- M5 ドラフト規則のクライアント写し: `client/data/config/m5_draft_rules.json`
- M5 ドラフト規則の読み込み・検証: `client/scripts/config/m5_draft_rules.gd` と `server/race_m5.py`
- 標準コースの正本: `shared/course_layout_m5.json`（クライアント写しは `client/data/course_layout_m5.json`）
- 走行計算: `client/scripts/local_race_math.gd`
- ゴールの描画部品: `client/scripts/presentation/goal_visual.gd`
- ドラフト HUD の整形部品: `client/scripts/presentation/draft_hud_formatter.gd`

オンラインの判定・走行計算は引き続きサーバーが担当する。`local_race.json` を変更してもオンライン側のバランスは変わらない。一方、M5 ドラフト規則はサーバーとクライアント表示が同じ値を読む契約なので、正本と写しを必ず同時に更新する。

## 設定の編集方法

`local_race.json` はクライアントを再起動して反映する。`m5_draft_rules.json` は `shared/` の正本を編集してからクライアント写しへ同じ内容を反映し、Godot クライアントと Python サーバーの両方を再起動する。設定は初回利用時に読み込み、実行中はキャッシュする。毎フレームの読み直しやホットリロードは行わない。

JSON にコメントや末尾の余分なカンマは書けない。項目を省略したり名前を変えたりせず、値を編集する。初期値は JSON だけで管理し、コード側に同じ初期値を重複して置かない。

### 出力・抵抗・ブレーキ

- `drive_level_min` / `drive_level_max`: ブレーキ側と駆動側のノッチ限界。
- `drive_level_step`: 1 操作分のノッチ差。現行は 1。
- `drive_force_by_level_kmh_per_s`: 0 番目がニュートラル、以降が各正ノッチの駆動加速度（km/h 毎秒）。要素数は最大ノッチ + 1。0 番目は 0、以降は非減少とする。
- `min_speed_kmh`: 現行の仮最低速度（km/h）。
- `rolling_resistance_kmh_per_s`: 速度によらない抵抗減速度（km/h 毎秒）。
- `air_resistance_quadratic_coefficient`: 速度二乗抵抗の係数。`coefficient × 速度（km/h）²` が減速度（km/h/s）になる。現行は `0.00120`。
- `brake_deceleration_per_level`: ブレーキ 1 ノッチ当たりの追加減速度（km/h 毎秒）。
- `drive_repeat_initial_s` / `drive_repeat_interval_s`: 押しっぱなし操作の初回待ち時間と反復間隔（秒）。

### ローカル CPU のライン・ペース変化

- `cpu_speed_tiers_kmh`: CPU の最高速ティア（km/h）の配列。最低速度以上・非減少・90以下を検証する。現行は近い集団を作りやすい `54 / 55 / 56`。
- `cpu_steer_reselect_min_s` / `cpu_steer_reselect_max_s`: 次のライン目標を選び直す間隔（秒）。現行は `1.0 / 2.0`。
- `cpu_steer_target_delta_max_m`: 一度のライン目標変更で、現在位置から動ける最大距離（m）。コース幅を横断する目標にはしない。
- `cpu_steer_speed_m_per_s`: CPU が目標ラインへ寄る速度（m/s）。
- `cpu_follow_forward_range_m` / `cpu_follow_lateral_range_m`: 前走者を追従候補として評価する前方・横方向の範囲（m）。現行は `20.0 / 4.0`。
- `cpu_follow_preferred_gap_m`: 追従時に保とうとする前方距離（m）。候補選択とペース補正の基準にも使う。
- `cpu_follow_offset_blend`: 選んだ追従スロットへ目標ラインを寄せる割合（0〜1）。
- `cpu_follow_slot_lateral_spacing_m`: 前走者の中央・内側斜め後方・外側斜め後方の3候補間の横幅（m）。
- `cpu_follow_slot_crowding_forward_range_m` / `cpu_follow_slot_crowding_lateral_range_m`: 各追従候補の混雑を測る縦横範囲（m）。他走者が候補位置に近いほど混雑スコアが増える。
- `cpu_follow_slot_crowding_weight`: 混雑スコアの重み。
- `cpu_follow_slot_inner_bias`: 内寄り基準に近い追従候補を選びやすくするスコアの重み。同点では内側、中央、外側の順で安定して選ぶ。
- `cpu_follow_max_pace_correction_kmh`: 追従時の目標速度補正の最大値（km/h）。現行は `1.4`。前方距離が遠いほど加算、近すぎるほど減算する。
- `cpu_follow_pace_saving_kmh`: 追従車間にいる時に、目標速度から引く温存分（km/h）。遠い時の追走・近すぎる時の減速も、同じ車間誤差式の範囲内で残る。これはローカルCPUのペース方針であり、スタミナ計算にはまだ接続しない。
- `cpu_inward_target_offset_m`: CPUが戻ろうとする内寄りの基準ライン（m）。負の offset は内側。
- `cpu_inward_target_blend`: 追従候補がない時、ランダムな小移動へ内寄り基準を混ぜる割合（0〜1）。
- `cpu_pace_baseline_max_offset_kmh`: CPU ごとに固定で持つ、最高速ティアからの最大巡航差（km/h）。現行は `0.5`。
- `cpu_pace_variation_min_s` / `cpu_pace_variation_max_s`: 一時ペース差を選び直す間隔（秒）。現行は `2.0 / 4.0`。
- `cpu_pace_variation_max_kmh`: 一時ペース差の最大振れ幅（km/h）。現行は `0.35`。最終目標は各 CPU の最高速ティアを超えない。

CPU はライン目標を 1〜2 秒ごとに選び直す時、近い前走者を距離・横差の同じ評価式で一頭選ぶ。追従先は真後ろ固定ではなく、中央・内側斜め後方・外側斜め後方の3候補を、前走者との車間、候補位置の混雑、内寄り基準で同じ式により評価する。候補がない時はランダムな小移動を内寄りへ戻す。追従車間では同じ車間誤差式に温存分を加え、遠い時の追走・近すぎる時の減速を保つ。近い最高速ティアと抑えた固定／一時ペース差により、追従の収束前に隊列が分断されにくい。目標の移動幅・変化間隔・速度幅はこの設定で必ず上限を持つ。これはローカル簡易レースで集団とドラフトを観察しやすくするための挙動で、CPU の性格・脚質や M5 オンラインの本実装ではない。

駆動加速度は実際の加速度そのものではない。実際には抵抗を引いて計算するため、同じノッチでも速度やドラフト状態で加減速が変わる。

出力走行中は HUD と 1 秒間隔の Godot ログに、推進力（負ノッチ時は制動寄与）、転がり抵抗、空気抵抗（二乗）、ドラフトによる空気抵抗軽減、計算加速度をすべて `km/h/s` で出す。これらは `LocalRaceMath.drive_diagnostics_kmh_per_s()` の同一結果を使う。

### M5 共通ドラフト規則

- `max_received_p`: 受け取れるドラフト効果の上限（割合）。現行は 0.24。
- `assist_max_kmh`: ドラフトによる速度補助の上限（km/h）。現行は 4.0。
- `chain_attenuation`: 前方相手が受けている効果を連鎖させる減衰率。現行は 0.7。
- `forward_min_m`: ドラフト対象として意味のある最小前方距離（m）。現行は 1.5mで、直径1.5mのぷるりんの中心同士が完全な横並び／重なり状態では受け取らないための境界。
- `forward_max_m`: 前方対象を調べる最大距離（m）。M5 の実効条件は **`forward_min_m <= gap <= forward_max_m`**。
- `lateral_range_m`: 横方向の判定範囲（m）。現行は 3.0m。
- `lateral_falloff_exponent`: 横差による寄与減衰の指数。`(1 - 横差 / lateral_range_m) ^ exponent` を直接・連鎖の両方へ使う。現行は 0.35 で、範囲端では0を維持しつつ、中間の横ずれは線形より緩やかに減衰する。

直接ドラフトは、前方最小・最大距離と横方向の範囲にいる**全走者**を寄与として使う。対象数の上限は置かず、距離の近い順、同距離ならID順でHUDの主対象と一覧を安定させる。受取率そのものは従来どおり `max_received_p` で上限を持つ。

### ローカル専有のドラフト係数

- `draft_air_resistance_factor`: 空気抵抗の軽減に使う係数（0〜1）。
- `draft_aggregation_exponent`: 個別対象の寄与を合成する p ノルムの指数。各寄与 `c_i` を最大受取率で正規化し、`min(1, (Σ c_i ^ exponent) ^ (1 / exponent))` としてから受取率へ戻す。対象数ごとの分岐は持たず、現行は `2.3`。
- `draft_response_exponent`: 合成後の受取率に適用する応答曲線の指数。現行は `2.0`。
- `draft_effective_max_ratio`: ローカル走行に載せる実効率の上限（0〜1）。正規化受取率を `r` とすると、実効率は `draft_effective_max_ratio × r ^ draft_response_exponent`。現行は `0.60` で、`r=0.5` は15%、`r=1.0` は60%になる。

ローカルM5もオンラインM5と同じく、レース進行値を基準に前方を判定する。移動・接触・ゴール判定後に全員分を一括計算し、次のtickで効果を使う。ゴール済みでも結果表示までは移動・接触・ドラフトの受給／供給を続けるが、着順とゴールタイムはゴール時点で固定する。ローカルHUDには直接対象のID・前方距離・横差、連鎖元、直接／連鎖／総合の受取率に加え、応答曲線後の実効率と、その実効率による速度上限補正を表示する。空気抵抗の軽減量と実加速度は出力診断行で別に確認する。実効率の応答曲線と上限はローカル専用で、M5／server の生の受給規則と速度適用は変更しない。

### スタミナ・心拍

- `heart_rate_rest_bpm` / `heart_rate_max_bpm`: 心拍目標の下限・上限（bpm）。
- `heart_rate_change_bpm_per_s`: 心拍が目標値へ近づく速さ（bpm 毎秒）。
- `stamina_capacity`: スタミナの上限。
- `stamina_low_effort_delta_per_s` / `stamina_max_effort_delta_per_s`: 現行の負荷補間に使うスタミナ増減量（毎秒）。正が回復、負が消費。

今回の外出しは既存の簡易状態計算を維持するためのもので、生理モデルの完成や再設計ではない。ニュートラル時の扱いなど、数式・条件分岐は走行計算側に残す。

## 不正な設定

必須項目、数値型、有限値、範囲、未知のキー、ノッチ数と配列長、心拍の整合性を検証する。標準コースはルート・数値・区間の基本整合性も検証する。不正な設定を別の初期値で黙って置き換えない。ローカル／M5 は開始前に人が読めるエラーを表示して中止する。

新しい項目や数式を追加するときは、JSON だけでなく検証・使用側・テストも更新する。`schema_version` は現在 1。

## 共通化の境界

ゴール演出はコースの Path・経路上の距離・コース幅を受け取る描画部品にまとめ、レースの進行やゴール判定から切り離す。コントローラーが配置距離を決め、描画部品が Path から位置・向きを求めて見た目を構築する。再配置してもノードは増殖しない（枠は作り直し、ライン・パネル・文字は再利用）。

設定ファイルに計算処理や実行コードは入れない。単位変換の定数や数式の構造まで無理に JSON 化しない。

## 後続作業

- ローカル簡易レースは検討事項 #28 により最大ノッチ 6・二乗抵抗を採用している。M5 オンラインの目標速度方式とサーバーは別仕様で、この JSON では変更されない。
- 標準コースの寸法は [`shared/course_layout_m5.json`](../shared/course_layout_m5.json) が正本。クライアント写しは `client/data/course_layout_m5.json`。ローカル 2000 m と M5 が読む。M4 だけ旧寸法をコードに残している。
- サーバーの係数・CPU 個性、接続先設定、コース JSON の配布方法は別途整理する。
- 入力・CPU 判断・状態計算・表示の分離は、回帰テストを追加しながら段階的に進める。
- 全設定の外出しが完了したわけではない。目標スピード方式の床や刻みなど、一部は引き続きコード内にある。

## 確認方法

Godot 4.7 の GUT で既存テストと設定検証・ゴール演出の回帰テストを実行する。さらに実機でローカル／オンライン両方のゴール表示と出力操作を確認する。自動テストと見た目の確認は区別して記録する。
