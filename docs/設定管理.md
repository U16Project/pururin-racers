# 設定管理と共通化

現行ローカルレースのステータス・数式・実行順を一つにまとめた参照資料は、[`現行ローカルレース計算リファレンス.md`](現行ローカルレース計算リファレンス.md) を正本の入口とする。

## 今回の対象

ローカルレースの出力操作に関する調整値を JSON に分離し、M5 の両側で同じ意味を持つドラフト規則と、ローカル／オンラインのゴール演出を共通化する。ローカルのノッチと抵抗のバランスは検討事項 #28 を正とする。

- ローカル走行設定の正本: `client/data/config/local_race.json`
- 読み込み・検証: `client/scripts/config/local_race_config.gd`
- ぷるりんの基礎ステータス・属性・脚質補正の正本: `client/data/config/pururin_stats.json`
- 読み込み・検証・有効値計算: `client/scripts/config/pururin_stats_config.gd` と `client/scripts/pururin_stats_math.gd`
- ローカル検証用の初期ロスター: `client/data/config/pururin_roster.json`
- ロスターの読み込み・検証: `client/scripts/config/pururin_roster_config.gd`
- M5 ドラフト規則の正本: `shared/m5_draft_rules.json`
- M5 ドラフト規則のクライアント写し: `client/data/config/m5_draft_rules.json`
- M5 ドラフト規則の読み込み・検証: `client/scripts/config/m5_draft_rules.gd` と `server/race_m5.py`
- 標準コースの正本: `shared/course_layout_m5.json`（クライアント写しは `client/data/course_layout_m5.json`）
- 走行計算: `client/scripts/local_race_math.gd`
- ゴールの描画部品: `client/scripts/presentation/goal_visual.gd`
- ドラフト HUD の整形部品: `client/scripts/presentation/draft_hud_formatter.gd`

オンラインの判定・走行計算は引き続きサーバーが担当する。`local_race.json` を変更してもオンライン側のバランスは変わらない。一方、M5 ドラフト規則はサーバーとクライアント表示が同じ値を読む契約なので、正本と写しを必ず同時に更新する。

## 設定の編集方法

`local_race.json` と `pururin_stats.json` はクライアントを再起動して反映する。`m5_draft_rules.json` は `shared/` の正本を編集してからクライアント写しへ同じ内容を反映し、Godot クライアントと Python サーバーの両方を再起動する。設定は初回利用時に読み込み、実行中はキャッシュする。毎フレームの読み直しやホットリロードは行わない。

JSON にコメントや末尾の余分なカンマは書けない。項目を省略したり名前を変えたりせず、値を編集する。初期値は JSON だけで管理し、コード側に同じ初期値を重複して置かない。

### ぷるりんの出走前ステータス

- `stat_ids`: `top_speed`、`acceleration`、`stamina`、`cardio`、`aero`、`pack`、`contact_resistance`、`handling` の8項目。順序もUI・保存・テストの共通契約とする。
- 配分は各 `1〜10`、合計 `40`。初期配分は全項目 `5`。
- `attributes`: 地水火風の属性ボーナス。各属性は2項目へ `+2` を加え、その2項目だけ出走前の上限が `12` になる。
- `running_styles`: 逃げ・先行・差し・追い込みの、対応順位組と4区間中の専用ボーナスを定義する。
- レース中は順位補正と区間補正を足し、有効値を `1〜15` に制限する。個体の保存・編集画面は後続作業とする。

ローカル簡易レースでは、最高速度・加速度・空力適性・集団適性を接続する。`local_race.json` の `top_speed_natural_min_kmh` / `top_speed_natural_max_kmh` は、有効最高速1／15かつ基準加速度5・ノッチ6・単独走行で自然に釣り合う速度で、現行は63／77km/h（間は1点ごとに1km/h。2026-10-03に61／75から+2）とする。個体ごとの速度上限には使わず、速度に応じた推進力補正で到達速度を作る。`acceleration_drive_force_bonus_per_stat_kmh_per_s`（正ノッチ時の推進力差）もここで調整する。空力適性は二乗空気抵抗だけを、集団適性はドラフト応答曲線後の実効率だけを補正し、いずれも有効値5を現行値とする。順位・区間補正を加えた有効値を毎フレーム読む。接触耐性・操作性は、対応する走行・接触システムを導入する段階で接続する。

### 初期ロスター

- `pururin_roster.json` は、ローカル検証で使う8体の初期ロスターである。導入画面で操作個体を1体選び、残る7体をCPUにする。初期選択は風・先行のヒカリ（`player-1`）である。
- 各個体は `id`、表示名、操作種別（初期表示用）、`trainer_profile_id`、属性、脚質、40点配分を持つ。操作種別はレース開始時の操作者を固定せず、選択されなかった個体は全員CPUとして走る。
- 全個体は既存 `local_race.json` の `cpu_trainer_profiles` を `trainer_profile_id` で参照する。ヒカリはCPU時に `balanced` を使う。個体の能力とトレーナーの作戦傾向を混ぜないためである。
- これはユーザーの所持個体を保存する機構ではない。所持スロット（最大5）とレシピ保存は、編集画面・永続保存を実装する段階で別データとして追加する。

### 出力・抵抗・ブレーキ

- `drive_level_max`: ノッチの最大値。ノッチは0〜この値（負ノッチは廃止し、制動はブレーキ操作）。
- `drive_level_step`: 1 操作分のノッチ差。現行は 1。
- `start_countdown_seconds`: ローカルレース開始前のノッチ選択カウントダウン（秒）。
- `player_start_drive_level`: カウントダウン開始時にプレイヤーへ入れるノッチ。現行は 4。
- `player_start_gate_index`: プレイヤーを置くゲート番号（0〜7）。残りのゲートをCPUへ順番に割り当てる。現行は `0`。
- `cpu_start_drive_level` / `cpu_start_drive_duration_seconds`: CPUが開始直後に使う共通ノッチと継続時間（秒）。ノッチは開始後もCPUの基本ノッチとして使う。CPUもプレイヤーと同じ駆動計算で発進する。
- `drive_force_by_level_kmh_per_s`: 0 番目がニュートラル、以降が各正ノッチの駆動加速度（km/h 毎秒）。現行は `[0, 6.0, 7.0, 8.6, 10.0, 11.6, 14.4]`（2026-10-03に2倍。転がり抵抗・空気抵抗・ブレーキと同じ倍率なので、各ノッチで落ち着く速度は変わらず、加速と減速だけが速くなる）。要素数は最大ノッチ + 1。0 番目は 0、以降は非減少とする。
- `min_speed_kmh`: 現行の仮最低速度（km/h）。
- `rolling_resistance_kmh_per_s`: 速度によらない抵抗減速度（km/h 毎秒）。現行は `1.1`（2026-10-03に `0.55` から2倍）。
- `air_resistance_quadratic_coefficient`: 速度二乗抵抗の係数。`coefficient × 速度（km/h）²` が減速度（km/h/s）になる。現行は `0.0045`（2026-10-02に `0.00120` から `0.00204` へ、2026-10-03にさらに2倍の `0.00408`、2026-10-07に `0.0045`）。0.0045への変更は、先頭を逃げる走者の有利を抑えるため。単独のノッチ4は約1km/h、ノッチ5は約0.8km/h遅くなる。ノッチ6の単独の速さは、最高速の補正が一緒に増えるので変わらない。ドラフトは空気抵抗の割合で効くので、集団の中の速さは、ほとんど変わらない（係数が大きいほど、ドラフトで減る量も大きい）。
- `aero_air_resistance_reference_stat` / `aero_air_resistance_multiplier_per_stat`: 空力適性による二乗空気抵抗の基準有効値と、1ポイントごとの倍率差。現行は `5 / 0.006`（2026-10-03に `0.015` から変更。空力5→15の効果が15ポイントで、集団ステータスの効果（前に2頭で11〜14ポイント）より大きく、集団の中が楽というバランスが崩れていたため）で、抵抗倍率は `1 - 0.006 × (空力適性 - 5)`。空力1は1.024、空力15は0.94になる。転がり抵抗・駆動力・速度上限には触れない。
- `pack_draft_effective_reference_stat` / `pack_draft_effective_multiplier_per_stat`: 集団適性によるドラフト実効率の基準有効値と、1ポイントごとの倍率差。現行は `5 / 0.12`（2026-10-03に `0.025` から変更。差が小さすぎて、集団1と15で実効率が83%と87%しか違わなかった）で、`x` へ `1 + 0.12 × (集団適性 - 5)` を掛ける（集団1で×0.52、5で×1.0、10で×1.6、15で×2.2）。生の受取率、対象判定、複数対象の集約、連鎖は変えない。実効率は、その結果を `x / (1 + x)` にし、増えるほど100%へ近づける。固定の上限値は置かない。
- `brake_deceleration_kmh_per_s`: ブレーキ操作を押している間の減速度（km/h 毎秒）。現行は `16.0`（2026-10-03に `8.0` から2倍）。ノッチとは独立で、押している間は有効な出力が0になる。
- `contact_lateral_range_m` / `contact_longitudinal_range_m`: ぷるりんの体の大きさ（m）。体は、前後がこの前後の範囲、横がこの横の範囲の楕円で扱い、前後ブロック・接触・押し合いの重なり判定に共通で使う。接触した相手を後ろへ押し戻す処理はない。
- `front_block_lateral_m`（現行 `0.75`、2026-10-06新設）: 前の走者の手前で止める（前後ブロック）のは、相手との横の差がこの値未満（真後ろに近い）のときだけ。それ以上の斜め・横の相手とは、前後では止めず、体が重なったら横の押し合いで解く。以前は、横の差が体の幅未満なら、少しでも後ろにいる側が止められ、相手の後ろへ下がっていた（接触耐性が効かなかった）。
- `block_approach_rate_per_s`（現行 `1.0`、2026-10-05新設）: 前の走者にふさがれたとき、残りの距離を1秒あたりどれだけ詰めるか。進める量は「前の走者の進む量 + 残りの距離 × この値 × フレーム時間」で頭打ちになり、前の走者の速さへなめらかに寄る。重ならないことは変わらない。大きいほど急に止まる。
- `contact_touch_margin_m`（現行 `0.3`）: 体の外側で、横に並んで接している（負荷がかかる）と数える幅。
- `contact_heart_load_bpm_per_s` / `contact_stamina_load_l_per_s`（現行 `0.7` / `0.02`）: 横に接している走者1人あたりの、心拍と体力への追加負荷（最大2人）。
- `contact_resistance_reference_stat` / `contact_resistance_multiplier_per_stat`（現行 `5` / `0.06`）: 接触耐性による負荷の倍率。基準有効値5で1.0倍、1ポイントごとに6%減り、下限は0.2倍。
- `push_load_multiplier`（現行 `3.0`）: 押し合いに入った走者（勝者も敗者も）の接触負荷の倍率。
- 押し合い（2026-10-06更新）: 勝ち負けは、接触耐性の大小だけで決まる。(1) 動く前の判定：新しい横位置が、前のフレームの位置にいる走者の体に入るとき、接触耐性が相手より高ければ入り、同じか低ければ体の縁で止まる。(2) 重なりの解消：体が重なったら（前へ進んで斜めに重なった場合を含む）、接触耐性が低い方が重なり全部ぶん横へ押し出され、同じなら半分ずつ離れる。高い方の動きは取り消さない。壁で動けない分は、相手が逆向きに動いて解く。「相手の方向へ動いているか」による強さの倍率は廃止した（`push_strength_per_stat`・`push_intent_multiplier`・`push_passive_multiplier` は削除）。両方が押し込み合って往復する（ぶれる）ことがない。
- `handling_steer_reference_stat` / `handling_steer_multiplier_per_stat`（現行 `5` / `0.05`）: 操作性による左右のライン移動の速さの倍率（基準5で1.0倍、1ポイントごとに5%）。プレイヤーとCPUで共通。操作性は、このほか、下の「左右に動く負荷」「カーブの中央からの遅れ」「ノッチ変更の負荷」「ドラフトの効く横幅」に効く。
- `lateral_move_heart_load_bpm_per_m` / `lateral_move_stamina_load_l_per_m` / `lateral_move_load_multiplier_per_stat`（現行 `0.4` / `0.01` / `0.05`、2026-10-05新設）: 左右に動いたときの負荷。自分の操作（CPUは進路どり）で横に動いた距離に比例して、心拍（1mあたり +0.4 bpm）と体力（1mあたり -0.01 L）に足す。押し合いで押し出された分と、止められて動けなかった分は数えない。操作性で倍率が変わる（基準5で1.0倍、1ポイントごとに5%減り、下限0.2倍）。速度には触れない。
- `drive_change_heart_load_bpm_per_level` / `drive_change_stamina_load_l_per_level` / `drive_change_load_multiplier_per_stat`（現行 `2.0` / `0.02` / `0.05`、2026-10-06新設）: ノッチを変えたときの負荷。変えた段数に比例して、心拍（1段あたり +2 bpm）と体力（1段あたり -0.02 L）に足す。上げるときも下げるときも同じ。操作性で倍率が変わる（基準5で1.0倍、1ポイントごとに5%減り、下限0.2倍）。プレイヤーはブレーキ中も選んでいるノッチで数え、CPUは実際に使うノッチで数える。レース開始の最初のフレームは数えない。
- `draft_lateral_range_multiplier_per_stat`（現行 `0.05`、2026-10-06新設）: 操作性による、ドラフトの効く横幅の倍率。受け取る側の効く横幅 = 共有規則の横幅（3m）×（1 + 0.05 × (操作性 − 5)）、下限0.5倍。操作性15で4.5m、1で2.4m。直接・連鎖の両方の効き方に使う。共有のドラフト規則（`shared/`）は変えず、ローカルの計算だけ。
- `line_speed_penalty_outer_edge` / `line_speed_penalty_inner_ratio` / `line_speed_penalty_reference_speed_kmh` / `line_speed_penalty_multiplier_per_stat`（現行 `0.02` / `0.5` / `60` / `0.05`、2026-10-06新設）: カーブで、コースの中央から離れるほど少し遅くなる。遅れ = 外側の端の遅れ（2%）× (中央からの距離 ÷ 端までの距離)の2乗 × (内側なら0.5) × (速さ ÷ 60km/h) × 操作性の倍率（基準5で1.0倍、1ポイントごとに5%減り、下限0.2倍）。内側は、距離倍率が小さい側。直線では遅れない。進む距離にかけるので、HUDの速度（実際に進んでいる速さ）にも反映される。内側の端の得（距離倍率で約3.5%）は、約2.5%に減る。
- `course_marker_sign_interval_m`（現行 `100`）: コースの内側に立てる距離標識の間隔（m）。標識は、白い四角い板に、赤い数字（残りの距離。「19」と小さい「00」）。標識と標識の中間の両脇に、コーンを1個ずつ置く。
- `drive_repeat_initial_s` / `drive_repeat_interval_s`: 押しっぱなし操作の初回待ち時間と反復間隔（秒）。

### ローカル CPU のライン・ペース変化

- `cpu_start_drive_level` / `cpu_start_drive_duration_seconds`: カウントダウン後、CPUが使う共通の開始ノッチと継続時間。現行はノッチ5を1秒。以後も同じノッチを基本とし、心拍が `cpu_heart_drop_threshold_bpm`（現行195）以上のときだけ下げる。
- `cpu_trainer_profiles`: CPUトレーナーのプロファイル定義。現行コードが読むのは `line_pref`（内寄り志向、0〜1）だけで、ライン候補の内側基準に使う。現行は `front 0.90` / `balanced 0.95` / `draft 1.00` / `late 0.70`。各個体は roster の `trainer_profile_id` で参照し、未定義IDはロスター検証で拒否する。
- `cpu_trainer_reselect_seconds`: CPUがノッチを見直す間隔（秒）。現行は0.8秒。
- CPUのノッチ判断（2026-10-03〜、2026-10-06更新）: 開始後も `cpu_start_drive_level` を基本ノッチとして維持する。現在心拍が `cpu_heart_drop_threshold_bpm`（現行195 bpm。200の少し手前）以上のときだけ、心拍が下がる最大ノッチへ下げる。下がるかどうかは、走者の心拍の計算と同じく、慣れと、接触・押し合い・横移動の負荷（1秒あたり）を含めて判断する。順位・距離・燃料・前走者による補正はない。旧トレーナー式の `cpu_trainer_*` 調整値は削除済み。
- `cpu_heart_drop_threshold_bpm`（現行 `195`、2026-10-06新設）: CPUがノッチを下げ始める心拍。200ちょうどで判断すると、ノッチ4のまま200のすぐ上に張り付き、熱で進む力が落ちる個体が出たため、少し手前にした。
- `cpu_steer_reselect_min_s` / `cpu_steer_reselect_max_s`: 次のライン目標を選び直す間隔（秒）。現行は `1.0 / 2.0`。
- `cpu_steer_speed_m_per_s`: CPU が目標ラインへ寄る速度（m/s）。
- `cpu_follow_forward_range_m` / `cpu_follow_lateral_range_m`: 前走者を追従候補として評価する前方・横方向の範囲（m）。現行は `20.0 / 4.0`。
- `cpu_follow_preferred_gap_m`: 追従時に保とうとする前方距離（m）。候補選択とペース補正の基準にも使う。
- `cpu_follow_offset_blend`: 選んだ追従スロットへ目標ラインを寄せる割合（0〜1）。
- `cpu_follow_slot_lateral_spacing_m`: 前走者の中央・内側斜め後方・外側斜め後方の3候補間の横幅（m）。
- `cpu_follow_slot_inner_midpoint_blend`: 現在ラインと内寄り基準の中間候補を作る割合（0〜1）。候補生成の係数をコードへ直書きせず、通常は `0.5`。
- `cpu_follow_slot_crowding_forward_range_m` / `cpu_follow_slot_crowding_lateral_range_m`: 各追従候補の混雑を測る縦横範囲（m）。他走者が候補位置に近いほど混雑スコアが増える。
- `cpu_follow_slot_crowding_weight`: 混雑スコアの重み。
- `cpu_follow_slot_inner_bias`: 内寄り基準に近い候補を選びやすくするスコアの重み。追従では、渡された `line_pref` のラインを内寄り基準にし、そのライン自体も他のスロットと同じ式の候補に入る。`line_pref` がない呼び出しだけ、共通の `cpu_inward_target_offset_m` を基準にする。現行は `1.7`。空きの直線で内側の基準が勝ち、追い抜き意図が強いときと内側が塞がっているときは外側候補が残る。これより小さいと外端に残り、`2.0` 以上では塞がった内側へも空きラインが入り込む。
- `cpu_line_distance_advantage_weight`: カーブ時の既存 `distance_multiplier` をCPUのライン候補スコアへ反映する重み。内側（負のoffset）は走行距離倍率が小さいほど選ばれやすくなる。直線では曲率が0のため差は発生しない。外側への追加スタミナ・心拍負荷は加えない。現行は `4.0`。
- `cpu_overtake_bias_threshold` / `cpu_overtake_slot_bias_weight`: CPUが前方の斜めスロットを候補に入れ、後方ドラフトより優先するための連続値の閾値・重み。積極性、温存志向、ドラフト志向、能力、速度差、スタミナから決まり、キャラ別の固定処理は持たない。現行は `0.05 / 1.5`。
- `cpu_overtake_forward_distance_m` / `cpu_overtake_slot_lateral_spacing_m`: 前走者の少し前へ出る通常候補の縦距離・横間隔。接触範囲に入る候補は採用せず、空きができるまで現在ラインを維持して再試行する。前が塞がっても出力を強制停止せず、進行だけを接触手前で止める。
- `cpu_overtake_escape_lateral_spacing_m` / `cpu_overtake_escape_bias_weight`: 通常の斜め前候補が混雑した時、外側へ大きく回って前方の空きを探す候補の横間隔・追い抜き意図の重み。内寄り・混雑と同じスコアで評価するため、常時外を回る固定処理にはならない。現行は `4.5 / 1.7`。
- `cpu_overtake_escape_steer_speed_multiplier`: 外回り候補を選んだ時だけ、通常の横移動速度へ掛ける倍率。走行ごとの操作性補正を後で同じ関数の倍率として渡せる。現行は `2.5`。
- `cpu_inward_target_offset_m`: CPUが戻ろうとする内寄りの基準ライン（m）。負の offset は内側。

CPU はライン目標を 1〜2 秒ごとに選び直す時、近い前走者を距離・横差の同じ評価式で一プル選ぶ。追従先は真後ろ固定ではなく、中央・内側斜め後方・外側斜め後方・外側へ大きく回る前方候補を、前走者との車間、候補位置の混雑、内寄り基準で同じ式により評価する。通常は内寄りを選び、周囲が混雑した時だけ前方候補（外回りを含む）が進路を確保する。候補がない時も、現在ライン・周囲密度・前方の空き・内寄り傾向を同じ連続スコアで評価する。内寄り基準が勝つときは、空いていても今の外側ラインを離れる。ノッチは別に、共通の基本ノッチを維持し心拍200以上でだけ下げる（上記「CPUのノッチ判断」）。距離ごとの固定イベントや意図的ミスは持たない。属性・脚質・ブースト・M5オンラインへの接続は今後の段階で行う。

駆動加速度は実際の加速度そのものではない。実際には抵抗を引いて計算するため、同じノッチでも速度やドラフト状態で加減速が変わる。

出力走行中は F3 の詳細表示（通常のHUDは速度・ノッチ・心拍・体力だけ）と 1 秒間隔の Godot ログに、推進力（ブレーキ時は制動寄与）、転がり抵抗、空気抵抗（二乗）、ドラフトによる空気抵抗軽減、計算加速度をすべて `km/h/s` で出す。これらは `LocalRaceMath.drive_diagnostics_kmh_per_s()` の同一結果を使う。

### M5 共通ドラフト規則

- `assist_max_kmh`: ドラフトによる速度補助の上限（km/h）。現行は 4.0。
- `chain_attenuation`: 前方相手が受けている効果を連鎖させる減衰率。現行は `0.5`（2026-10-02に `0.7` から変更。M5/server と共有）。
- `wake_base_p` / `wake_speed_reference_kmh` / `wake_speed_gain_p`: 走者が作る後方の影響量。`base + max(速度, 0) / reference × gain` で速度に応じて増える。走者側・受取側ともに上限は置かない。`base + gain` は基準速度時に真後ろの1走者が作る量であり、ローカル実効率とHUDの基準単位としてのみ使う。対象数やキャラクターごとの分岐は置かない。現行は `0.06 / 75.0 / 0.12`。
- `forward_min_m`: ドラフト対象として意味のある最小前方距離（m）。現行は 1.5mで、直径1.5mのぷるりんの中心同士が完全な横並び／重なり状態では受け取らないための境界。
- `forward_max_m`: 前方対象を調べる最大距離（m）。M5 の実効条件は **`forward_min_m <= gap <= forward_max_m`**。
- `lateral_range_m`: 横方向の判定範囲（m）。現行は 3.0m。
- `lateral_falloff_exponent`: 横差による寄与減衰の指数。`(1 - 横差 / lateral_range_m) ^ exponent` を直接・連鎖の両方へ使う。現行は 1.0（2026-10-03に 0.35 から変更）で、横ずれに比例して直線的に弱まる（体1つぶん＝1.5mずれると半分、3mで0）。0.35 では1.5mずれても78%効いてしまい、ずれによる弱まりが緩すぎた。この値は M5 サーバーと共有する。

直接ドラフトは、前方最小・最大距離と横方向の範囲にいる**全走者**を寄与として使う。対象数・受取率の上限は置かず、距離の近い順、同距離ならID順でHUDの主対象と一覧を安定させる。

### ローカル専有のドラフト係数

- `draft_air_resistance_factor`: 空気抵抗の軽減に使う最大の係数（0〜1）。実効率に掛けて、空気抵抗をどれだけ減らすかを決める。現行は `0.80`（2026-10-03に `0.40`、`0.50`、`0.55` を経て変更）。ドラフトで空気抵抗が減る割合の上限で、100%未満に保つ（100%を超えると空気抵抗がマイナスになり、速く走るほど押されて速度が暴走する）。`0.55` では集団ステータスが高くても低くても約55%の天井にぶつかり、差が小さかったため引き上げた。前に5頭で、集団1／5／10／15の空気抵抗の減りは 40／53／61／65%。
- `draft_aggregation_exponent`: 個別対象の寄与を合成する p ノルムの指数。`(Σ max(0, c_i)^exponent)^(1/exponent)` として受取率へ戻す。対象数・合算値の上限は持たず、現行は `0.7`（2026-10-02に `2.3` から仮採用）。指数が1未満のとき、合成結果は各寄与の合計を超え得る。1対象は指数の影響を受けない。入力チェックは `0.5`〜`4.0`。
- `blocked_speed_excess_max_kmh`（2026-10-03新設、現行 `8.0`）: 前の走者にふさがれている間に、出力上の速度が実際に進んでいる速さを上回れる最大の差（km/h）。ドラフトで出力上の速度だけが上がり続け、前が空いた瞬間に急加速する（実機の記録で2秒に+17km/h）のを防ぐ。上限までは溜まり、抜け出しの加速に使われる（最大約+8km/h）。完全にふさがれても、最低速度（`min_speed_kmh`）は下回らない。
- `rear_assist_range_m` / `rear_assist_transfer_rate` / `rear_assist_aero_multiplier_per_stat`（2026-10-03新設）: 後ろの走者から、前の走者が受ける効果（後方支援）。後方 `draft_rules` の前方最小距離（1.5m）から `rear_assist_range_m`（現行5m）まで、横は共有ドラフト規則の横幅（3m）以内の全走者から、離れ具合に応じて直接受ける（連鎖しない。元になる値は後ろの走者の出力上の速度から決まる wake）。受取量を基準比にして `x = 比 × 空力倍率` とし、空気抵抗の減る割合 = `rear_assist_transfer_rate × x / (1 + x)`。`rear_assist_transfer_rate`（現行 `0.10`）が最大の減り。空力倍率は `1 + rear_assist_aero_multiplier_per_stat（現行 0.12）× (空力 - 5)`。ドラフトとは `1 - (1 - ドラフトの減り) × (1 - 後方支援の減り)` で合成し、100%を超えない。測定では、空力5→15で増える分は約1.8〜1.9ポイントで、集団5→15のドラフト（前に1〜2頭で約6〜14ポイント）の約2割。
- `draft_response_reference_scale`: 応答曲線の基準を、HUD表示の基準（真後ろ1走者の wake）の何倍に置くか。現行は `3.0`（2026-10-03新設、`2.5`→`1.5`→`3.0`と調整）。大きいほど少頭数では効きにくく、天井に達しにくい。`1.5` では集団適性ごとの差が天井に隠れたため、集団適性の補正（上の `0.12`）と合わせて `3.0` にした。前に5頭（受取約4.7）で、集団適性1／5／10／15の実効率は 50／66／76／81%（ゲージ6／7／8／9段）。
- `draft_response_exponent`: 合成後の受取率に適用する応答曲線の指数。現行は `1.5`（2026-10-03に `2.0` から `1.0` を経て `1.5` へ。大きいほど弱いドラフトが効きにくく、集団で効きが伸びる。`2.0` は2頭で頭打ち、`1.0` は大集団の利点が薄れたため、中間の `1.5` を採用）。
- ローカルの実効率は、受取率を `wake_base_p + wake_speed_gain_p` で割った基準比 `r` に対し、`x = (r ÷ draft_response_reference_scale) ^ draft_response_exponent × 集団適性倍率`、実効率は `x / (1 + x)`。受取率は丸めない。実効率は固定上限ではなく、増えるほど100%へ近づく。

ローカルM5もオンラインM5と同じく、レース進行値を基準に前方を判定する。移動・接触・ゴール判定後に全員分を一括計算し、次のtickで効果を使う。ゴール済みでも結果表示までは移動・接触・ドラフトの受給／供給を続けるが、着順とゴールタイムはゴール時点で固定する。ローカルHUDには直接対象のID・前方距離・横差、連鎖元、直接／連鎖／総合の受取率に加え、応答曲線後の実効率を表示する。ドラフトは個体ごとの速度上限を上げず、空気抵抗の軽減量と実加速度を出力診断行で確認する。空気抵抗の軽減は抵抗そのものを超えない。実効率の応答曲線はローカル専用で、`x / (1 + x)` により100%へ近づく。M5／server は生の受取率を速度補助へ線形に載せ、個体の最高速は超えない。最高速補正は、ドラフト後に残る空気抵抗と空力倍率を含めて計算する。

### ダッシュとブースト（2026-10-06新設。プレイヤーだけ）

どちらも、一時的に推進力へ倍率をかける（`推進力 ×（1 + ダッシュの効き + ブーストの効き）`）。抵抗・ドラフトには触れない。推進力が増えるので、加速と、そのとき出せる最高の速さの両方が上がる。押した瞬間だけ有効（押しっぱなしは無効）。ノッチ0・ブレーキ中は発動しない。CPUは使わない。操作は、ダッシュがゲームパッドB／キーボードZ（2026-10-07に、Aから変更。Aは、カメラを左へずらす操作に、前から使っていたため）、ブーストがゲームパッドX／キーボードX。

- `dash_duration_s`（現行 `2.0`）: ダッシュが効く時間。最後に押してから数える。連打しても効きは重ならず、時間が延びるだけ。
- `dash_thrust_bonus` / `dash_thrust_per_acceleration_stat` / `dash_thrust_per_handling_stat`（現行 `0.20` / `0.03` / `0.02`。効きは2026-10-07に `0.30` から変更）: ダッシュで増える推進力の割合。`0.20 ×（1 + 0.03 ×（加速 − 5）+ 0.02 ×（操作性 − 5））`。
- `dash_stamina_multiplier` / `dash_heart_rise_multiplier`（現行 `5.0` / `3.0`）: ダッシュが効いている間の、体力の減る速さと、心拍の上がる力の倍率。実機で、連打しっぱなしが割安だったため、`1.5 / 1.2` から段階的に上げた。
- `boost_max_uses`（現行 `3`）: 1レースに使える回数。
- `boost_duration_s` / `boost_points_per_use` / `boost_stack_bonus`（現行 `3.0` / `300` / `0.2`）: ブーストはポイントで持つ。1回押すと300pt。ポイントは、最後に押してから3秒で、ちょうど0になるように、まっすぐ減る。効いている間に押すと、`300 + 残り ×（1 + 0.2）` になり、残り時間が3秒に戻る（早めに重ねるほど、割り増しが大きい）。
- `boost_thrust_per_point`（現行 `0.001`。300ptで +30%）: 1ptあたりの、増える推進力の割合。2026-10-07に、300ptで +50% から、+20%、+40% を経て変更。体力が残っているうちに3回重ねると、100km/h前後まで出ていたため。
- `boost_stamina_factor_min`（現行 `0.8`。2026-10-07に `0.6` から変更）: 残りの体力による、ブーストの効きの係数。満タンで1.0、体力0以下でこの値。終盤に体力が尽きてから使うと、ほとんど効かなかったため、落ち込みをゆるくした。
- `boost_heart_cost_bpm` / `boost_stamina_cost_l`（現行 `0` / `0.5`。2026-10-07に `8` / `1.0` から変更）: 使った瞬間に払う、心拍と体力。3回続けて使うと、心拍が+24されて上限に着いていたため、心拍の分はなくした。
- `boost_stamina_multiplier` / `boost_heart_rise_multiplier`（現行 `1.2` / `1.1`。2026-10-07に `2.0` / `1.5` から変更）: 効いている間の、体力の減る速さと、心拍の上がる力の倍率。ブーストは3回しか使えないので、負荷の小さい「ボーナス」の位置づけにした。
- `boost_debt_penalty_scale`（現行 `0.5`）: 効いている間、体力の負債による推進効率の低下を、この割合にする（半分）。

### スタミナ・心拍

- `heart_rate_min_bpm` / `heart_rate_normal_max_bpm` / `heart_rate_overheat_max_bpm`: 共通心拍の下限、通常上限、オーバーヒート時の頭打ち。現行は `100 / 200 / 230`。
- `heart_rate_rise_rate_by_drive_level_bpm_per_s`: ノッチ0〜6の心拍上昇率（bpm/s）。ノッチ0は0、正ノッチは単調増加させる。現行は `[0.0, 1.5, 2.5, 3.48, 4.63, 9.0, 13.0]`。2026-10-03に、低ノッチから高ノッチへ自然に増すカーブとして仮採用した。ノッチ1〜3は温存・微調整、ノッチ4は長時間では200 bpm超過を意識する巡航、ノッチ5・6は明確な高負荷として扱う。200超過後のペナルティは変えていない。
- `heart_rate_drive_load_scale`: ノッチ別基礎上昇率を自然回復項と釣り合わせるための負荷倍率。現行は `0.58`。この値でノッチ4／5／6の定常域を調整する。
- `heart_rate_recovery_exponent`: 自然回復率の心拍減衰指数。回復率は、心拍が100〜230のどの辺りか（0〜1）の指数乗に比例する。大きいほど、低〜中の心拍で回復が弱く、心拍が高く止まる。現行は `1.3`（2026-10-05に `1.2` から `1.0`、`1.3` へ。最高の心拍を、アカネ（心肺8）のノッチ5でも200を超えるように上げるため）。
- `heart_rate_recovery_rate_scale`: 心拍が下がる方向へ働く自然回復率の倍率。高心拍からの回復を速めるが、100 bpm付近では指数減衰により穏やかに収束する。現行は `2.75`。
- `heart_adaptation_recovery_gain` / `heart_adaptation_time_s`（現行 `1.6` / `40` 秒、2026-10-05新設。効きは2026-10-07に `2.0` から `1.5`、`1.7` を経て `1.6`）: 慣れ。0〜1の値で、心拍が高い状態が続くほど、約40秒かけて、心拍が100〜230のどの辺りかの割合へ近づく。自然回復率に `1 + 効き × 慣れ` を掛けるため、同じノッチを入れ続けても、最高の心拍に達したあと、ゆっくり下がる。上昇負荷には触れない。慣れはレース開始時に0へ戻す。 効き2.0では、ノッチ5を続けても90秒ごろに心拍が200を下回り、心拍の歯止めがゆるくなって、体力の多い個体だけがノッチ5を長く続けられた。1.5では、ノッチ5を続けると、ほぼ最後まで200以上になる（心肺5で最高約218）。ノッチ4は200を超えず、最高約177から少し下がる。
- `heart_rate_rise_time_cardio_min_s` / `heart_rate_rise_time_cardio_max_s`: 心肺1／15で、ノッチ別上昇率へ掛ける補正の基準時間。仮採用は `13 / 20` 秒（従来 `11 / 25`、心肺5は15秒のまま）。到達時間そのものではない。現行のノッチ6・心肺5では、100 bpmから200 bpm到達まで約16.4秒、230 bpm到達まで約23.6秒。
- `heart_rate_recovery_time_cardio_min_s` / `heart_rate_recovery_time_cardio_max_s`: 心肺1／15で自然回復率の大きさを決める基準時間。現行は `31.5 / 25.5` 秒（2026-10-05に `27 / 22` から、`21 / 17`、`24 / 19.5` を経て変更。心肺5は約29.8秒）。値は心肺1〜15を連続補間する。100 bpmへは漸近するため、200から100へ戻り切る所要時間ではない。
- `stamina_capacity_base_l` / `stamina_capacity_per_stat_l`: 燃料タンクの基本容量とスタミナ1点あたりの容量（L）。現行は `18 + 1.0 × 出走前スタミナ` L（スタミナ1／5／8／15は `19 / 23 / 26 / 33L`）。2026-10-06〜07に、1点あたりの量を `3` から `2`、`1.5`、`1.0` へ下げ、そのあと基本の量を `15` から `17`、`18` へ上げた。負債も同じ量まで入れ、負債による推進効率の低下も「負債 ÷ 最大値」の割合で決まるため、スタミナの差は、プラス側・負債の限度・負債の落ち方の3か所に効く。1点あたりを小さくして、個体の差を抑えた。基本の量を上げたのは、後ろから行く走り方でも、ゴールの10〜15秒前に負債の限度に着いて失速していたため。
- `stamina_debt_capacity_multiplier`: 使い切った後に許容する負債を容量に対する倍率で決める。現行は `1.0`、つまり `-容量L` まで。負債効率は負債率だけで決まり、スタミナ値による二重の軽減は使わない。
- `stamina_consumption_min_l_per_s` / `stamina_consumption_max_l_per_s`: 正ノッチ時の基礎燃料消費量（L/s）。心拍係数と200超過時の倍率は掛けるが、スタミナ値による燃費補正は掛けない。基礎値は `0.0457142857142857 / 0.1828571428571428L/s`。
- `stamina_consumption_load_multiplier`: 基礎燃料消費へ掛ける倍率。現行は `1.20`。共通シミュレータでは同じキーを `config_overrides` で差し替える。
- `stamina_heart_rate_factor_min` / `stamina_heart_rate_factor_max`: 心拍100／200に対応するスタミナ消費係数。現行は `0.75 / 1.25`。
- `stamina_debt_efficiency_min`: 燃料負債が最大の時の操作由来効果の下限。現行は `0.55`。負債率に応じて連続補間する。
- `overheat_stamina_multiplier_max`: 心拍200〜230のオーバーヒート率に応じたスタミナ消費倍率の最大値。現行は `1.50`。
- `overheat_propulsion_efficiency_min` / `overheat_exposure_efficiency_loss_per_s`: 心拍200超過の加重継続負荷による推進効率の下限と、負荷1秒あたりの効率低下量。現行は `0.50 / 0.010`。210より220、220より230 bpmで速く負荷が蓄積し、230 bpmでも低下は継続する。
- `overheat_exposure_recovery_per_s`: 心拍が200 bpm未満のとき、200から低いほど速く200超過負荷を解消する基礎係数。現行は `2.50`。
- ノッチ0では心拍だけが下がり、スタミナは自動回復しない。ブレーキ中も心拍上昇・スタミナ消費の入力にはしない。

心拍は常に `ノッチ負荷−自然回復` の一つの式で連続的に変化する。ノッチ負荷は設定ファイルのノッチ別上昇率へ負荷倍率を掛け、自然回復は現在心拍が高いほど大きく、100 bpmに近づくほど小さくなる。心拍が下がる方向では `heart_rate_recovery_rate_scale` を掛ける。正ノッチでは両者の釣り合いでノッチごとの定常域へ収束し、ノッチ0・負ノッチでは自然回復だけが働いて100 bpmへ漸近する。心肺ステータスは基礎上昇率・回復速度を変える。速度・空気抵抗は今回の心拍計算へ直接加えない。心拍が高いほどスタミナ消費が増え、スタミナが0未満になると負債率に応じて後続の操作由来効果を連続的に失効させる基盤へ接続する。接触・ブースト・急なノッチ変更による追加負荷は後続段階で同じ入力経路へ追加する。

## 不正な設定

必須項目、数値型、有限値、範囲、未知のキー、ノッチ数と配列長、心拍の整合性を検証する。標準コースはルート・数値・区間の基本整合性も検証する。不正な設定を別の初期値で黙って置き換えない。ローカル／M5 は開始前に人が読めるエラーを表示して中止する。

新しい項目や数式を追加するときは、JSON だけでなく検証・使用側・テストも更新する。`schema_version` は現在 1。

## 共通化の境界

ゴール演出はコースの Path・経路上の距離・コース幅を受け取る描画部品にまとめ、レースの進行やゴール判定から切り離す。コントローラーが配置距離を決め、描画部品が Path から位置・向きを求めて見た目を構築する。再配置してもノードは増殖しない（枠は作り直し、ライン・パネル・文字は再利用）。

設定ファイルに計算処理や実行コードは入れない。単位変換の定数や数式の構造まで無理に JSON 化しない。
