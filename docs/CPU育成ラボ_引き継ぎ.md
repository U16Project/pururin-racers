# CPU育成ラボ — 引き継ぎ（2026/10/22）

ユーザーと相談して決めた、CPU育成ラボの考え方。**ここに書いたことは、すべて仮の決め方**。作る人（エージェント）も、試しながら、よりよい形を探して、ラボそのものを改善していってよい。ただし、ゲーム本体の設定やCPUを書き換えるときは、必ずユーザーに確認を取ること（下の「守ること」）。

## ねらい

- 1つの画面（ラボ）の中で、CPUを育てて強くする。
- CPUたちは、レースの結果を元に、自分たちで良し悪しを判断し、次の代へつなげる（人やAIが「これが良い」と決めるのではなく、結果からコードが決める）。
- ある程度育ったら、ゲーム本体のCPUに取り込める。
- ユーザーは、育成中のCPUと一緒に走りたい。人が作った部屋にも、訓練中のCPUを送り込みたい。

## 学習のしかた（ユーザーが選んだ「(ア)」）

- CPU1体ぶんの「頭」は、**状況ごとの重みと線の数字のひと組**。
- レース中、頭は毎回まわりの状況を数字で見て、判断ごとに「状況の数字 × 重み」を足し合わせて点を出し、線を超えたらその操作をする。
- 育てるのは、この重みと線の数字。勝った頭を残し、少し変えた子・2つを混ぜた子を作って、くり返す。
- 型（逃げ・先行・差し・追い込み）ごとに育てる（前から「数値は型ごとに書く」と決めている）。
- 足し算だけだと「AとBが両方そろったときだけ」の判断が苦手なので、組み合わせの項目（例：残りが短い かつ 体力が多い）も見るものに足せるようにする。
- ほかのやり方（「もし〜なら〜」の決まりの並びを育てる、本格的なAI、人の操作のまね）も比べた。今は(ア)で始める。ただし、走らせる・点を付ける・保存する・比べる・取り込む の部分は、頭のやり方を替えても使い回せる作りにしておく（あとで頭の部分だけ替えられるように）。
- 本格的なAI（Python など）を入れる話は、ユーザーの確認なしに進めない（入れるものが要るため）。

## 頭が見るもの：**全部**

- ユーザーの指示は「全部使え」。今のレースで0.5秒ごと（オンラインは位置0.1秒・状態0.5秒ごと）に採っている値を、**自分のものも、まわりの全員のものも**、全部見る。
- ほかのぷるりんの体力・心拍も、順位表に出ているので見てよい。能力もパドックで公開されているので見てよい（人に見えない情報は無い）。
- 採っている値（`runner_local_race.gd` の `get_snapshot` と `get_telemetry_snapshot`）：
  - 位置・速さ：進んだ距離、コースの位置、ライン（中央からのずれ）、向き、出力上の速さ、実際の速さ、自然な最高速
  - 操作：ノッチ（出力）、ブレーキ、ダッシュ中か、ブーストの残り回数・たまり具合
  - 体：体力（量・入れ物・割合・減りやすさ）、心拍、心拍の上限超え、過熱の割合、推す力の効き
  - 風・集団：自分の風よけ、前から直接もらう風よけ、列で伝わる風よけ、合わせた風よけ、だれからもらっているか
  - ぶつかり：ぶつかりの数、押し合い中か、ぶつかり・横移動で上がる心拍、ぶつかりへの強さ
  - 自分の能力：8つの能力（最高速・加速・スタミナ・心肺・空力・集団・接触・操作）、属性、脚質、順位と区間で変わる実際の能力
  - レース：距離、残り距離（割合）、直線かコーナーか、順位、前後との差、まわりの混み具合
- 見るものは、ラボの画面で「使う・使わない」を入り切りできるようにし、育ったら効いていない項目（重みがほぼ0）が分かるようにする。

## 判断すること

ノッチを上げる・下げる、ラインを内・外へ、ブレーキ、ダッシュ、ブースト。

## 点の付け方（良し悪しは、コードが結果から決める）

- ユーザーの考え：**1位の割合がダントツで重い**。その次が **1位とのタイム差**。着順・残り体力なども見る。
- 仮の式：点 ＝ 1位の割合×100 － 1位とのタイム差の平均（秒）×5 － 平均の着順×2 － ゴールで残った体力の割合×3
- **今すぐ全部を決めなくてよい**（ユーザーに決定を急かさないこと）。ラボの画面で、いつでも項目を足し、重さを変えられる作りにする。仮の候補：2着・3着以内の割合、距離ごとのばらつき、心拍の上限超えの時間、ぶつかりの多さ、風よけをもらった時間、最後の直線での伸び、先頭にいた時間、相手の強さ。
- 「たまたま勝った」を除くため、1体を何十レースも、いろいろな距離・相手で走らせ、平均で決める。

## 流れ

1. 頭を作る（型ごとに20体ほど。最初は今のCPUに近い数字か、でたらめ）。頭1つ＝ファイル1つ。
2. 走らせる（画面なし・早回し。相手は今のゲームのCPUや、ほかの頭）。
3. 点を付ける（コードが計算）。
4. 次の代を作る（点の高い頭を残し、少し変えた子・混ぜた子で数を戻す）→ 2へ。
5. 確かめる（その代のいちばんを、まだ使っていない別のくじの番号で、今のゲームのCPUと走り比べ。決めた差以上で勝てば合格）。
6. 画面で見る（合格した頭の走りを画面ありで再生して、変な勝ち方＝計算のすきを使っていないか、ユーザーが目で確かめる）。
7. 取り込む（**ユーザーが「よし」と言ったときだけ**、ゲームのCPUの設定に書く。前の数字は履歴として残す。書く前に、何がどう変わるかを表で見せる）。

- ゲームのCPUも、ラボの頭も、同じ「判断のプログラム」で動かす（ラボで育った強さが、ゲームでもそのまま出るように）。
- 頭のファイル・成績は、ゲームの書き出しに入れない場所に置く。

## 人と走る・送り込み

- ラボの画面で、送り込む頭・つなぐサーバー（さくらの公式・自分のPC・だれかのサーバー、どこでも）・入る部屋を選ぶ。
- 送り込める所：**全部**（ともだち対戦の部屋も、オンラインフリー対戦のルームも）。フリー対戦では、人と同じにエントリーし、番が来たら自動で「入る」と答える。
- 名前に **「（訓練中CPU）」** と付けて、分かるようにする。
- 部屋の主は **断れない**。入れる数に **上限は付けない**（部屋の席の数まで）。
- しくみ：頭の数字（小さなファイル）を、部屋に入るときに**1回だけ**サーバーへ渡す。レース中は、サーバーの中でその頭が走る（今のCPUと同じ。ラボから操作を送り続けたりはしない）。終わったら、サーバーが結果をラボへ返し、ラボが点に入れる。
- サーバーの仕組みはゲームのアプリにも入っているので、同じ版のサーバーなら、どこでもこの受け取り方が使える。

## 今日わかったこと（2026/10/22、このPCで測定）

- 今のCPU：ノッチはスタートから最後まで決まった1つの段（心拍が上がりすぎそうなときだけ下げる）。ラインは前の後ろにつくか空きへ。ダッシュ・ブースト・ブレーキは使わない。残り距離や順位で走り方を変えることは、ほぼしていない。中身は `client/scripts/cpu_trainer_math.gd` と `runner_local_race.gd` の `_update_inputs`・`_update_cpu_drive_level`。
- 速さ：画面なし・`--fixed-fps 30`（実時間に合わせず、1コマ1/30秒で回せるだけ回す）で、1本ずつだと実時間の約13倍（2000mで約11秒）。8本同時（このPCは8コア）で、2000mが8本で約25秒＝1分に約19本。1代＝20体×40レース＝800レースで、約40分。
- 気づいた点：
  - 今のCPUは、ラインを選ぶ所でくじ（`randf()`）を使っている。同じ条件で比べるには、くじの番号をそろえる仕組みが要る。
  - ぷるりんの能力の差が、結果に数秒出る。比べるときは、同じぷるりんどうしで比べる（または入れ替えて走らせる）。

速さを測ったときのやり方（作業用の道具。ゲームのファイルは変えていない）：オンラインのサーバーと同じように、出走の一覧（`OnlineServer._entry` と `_with_runner_ids`）を作り、`RaceSession.select_distance`・`set_course_only(true)`・`set_online_entries` のあとで `local_race.tscn` を作り、人の席を `release_remote_runner` でCPUに渡して、`is_race_over()` まで毎コマ回し、`_race_elapsed` と `online_result_rows()` を読む。起動は `godot --headless --fixed-fps 30 --path client -s <道具>.gd`。

## 守ること

- ゲーム本体の設定（`client/data/config/` の JSON）やCPUの動きを、ユーザーの確認なしに変えない。取り込みは、必ずユーザーの「よし」のあと。
- 変な設定を勝手に決めない。決めたことは、短く、普通の言葉で報告する。
- 話し方・進め方の決まりは、リポジトリの `CLAUDE.md` のとおり（結論を先に、短く、専門用語は使わない、など）。
- ユーザーが何か言ったとき、すぐそれに合わせて「それがおすすめです」と自分の意見を翻さない。自分の考えは考えとして持ち、ユーザーの案と違うなら違うと言う。ユーザーの案のほうが良いと思ったときは、「ユーザーの案のほうが良い。理由は〜」と、どちらの案かをはっきりさせて言う。
- 入れるもの（道具・部品）が要る案は、何をどこへ入れるかを毎回書く。
