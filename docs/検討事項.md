## 2. 能力ポイントの総量・再配分ルール

**状態:** 未決

### 論点

「考えて勝つ」の中心が能力配分なのに、**何ポイント配れるか／後から変えられるか**が未定義。  
ポイント消費カーブ（高ステほど高い）も設計案から削除済みで、代替ルールも未定。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 固定プール（例: 合計 100）。作成時に配分。以降はレース用の作戦だけ変更可 |
| **B** | 固定プール＋「リセット」は冷却時間または回数制限付き |
| **C** | レース勝利などでプールが増える（成長）。見た目報酬と分ける |

### 私案

**A を基本、B を緩和策。**  
C は「育成で強い個体を作る」に寄りやすく、ガチャ無しでもパワーインフレしやすい。  
まず **総ポイント数と各ステの上限** を仮決めし、8プル対戦で触って調整するのがよい。

**仮提案（議論用）:**

- 配分可能ポイント: 80〜100
- 各ステ上限: 100（属性ボーナスで実効が上振れ可）
- 極端ビルドは可能だが、何かが必ず欠ける

### 私案２

**A に寄せつつ、ルールを一段具体化する（最優先で詰める項目）。**

消費カーブを復活させるより、次の方が説明しやすい:

| ルール | 仮 |
|--------|-----|
| **基礎値** | 全ステに同じ初期値（例: 各 30） |
| **配分プール** | 追加で振るポイント（例: 40） |
| **上限** | 各ステ 100（属性ボーナスは別枠で実効加算） |
| **再配分** | β は無料リセット可（デバッグ・調整優先）。正式版で B（冷却／回数）へ |

理由: 「高ステほど高い」は体感しにくい／説明コストが高い。基礎＋プールなら極端ビルドも残しつつ、最低限の万能性でレースが壊れにくい。  
**数値は仮。8プルプロトで必ず触って直す前提。**

## 4. レース報酬（ガチャなしで何を渡すか）

**状態:** 未決

### 論点

能力はポイント配分で決める方針なので、報酬でステを直接強くしすぎない方がよい。  
一方、何も無いと「次のレース」以外の目的が薄い。

### 選択肢（組み合わせ可）

| 報酬種 | 内容 | 能力への影響 |
|--------|------|--------------|
| 見た目パーツ | 目・口・眉・ほっぺ | なし |
| 模様 | 属性・季節・イベント | なし |
| 称号・記録 | 連勝、特定脚質など | なし |
| 通貨 | 改名・スロット解放など | 間接のみ |
| 能力ポイント | プール増加 | **あり（要注意）** |

### 私案

**見た目・称号・記録を主報酬。能力ポイント増加はβでは入れない（またはごく少量）。**  
「同じ条件から作戦で勝つ」を守る。

### 私案２

**能力ポイント増加は β・正式とも「原則なし」に寄せる（私案より厳しめ）。**

| 渡す | 渡さない |
|------|----------|
| 表情・模様・称号・戦績 | ステ強化、ステ解放ガチャ |
| 改名チケット等の軽通貨（任意） | 勝たないと強くなるループ |

理由: 「ごく少量」は後からインフレの抜け穴になる。継続欲は **見た目と記録** で足りる設計に寄せた方が、いまの方針と一貫する。  
順位表・リプレイ視聴・脚質別成績など「見る報酬」も有効。

## 6. マッチングとレーティング

**状態:** 未決

### 論点

10 分サイクル＋受付は「同時開催のロビー」型。  
レーティングを入れると公平性は上がるが、待ち時間と実装が重い。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | レーティングなし。来た人＋CPU で 8プル |
| **B** | 簡易レート（勝ち越しで帯が変わる程度） |
| **C** | 本格 MMR マッチ（同レート帯優先） |

### 私案

**β は A。**  
人が少ないうちは C は成立しにくい。データが溜まってから B を検討。

### 私案２

**同意（β＝A）。「公平さ」はレート以外で出す。**

- 受付締切時の CPU 補充で常に 8プル（設計案どおり）
- 戦績は見えるが、マッチ分けには使わない
- 実力差の不満が出たら、先に **練習** と **作戦フェーズの説明** を厚くする

B は同時接続が安定してから。C は長期見送りでよい。

## 13. 作戦フェーズで何をロックするか（新規）

### 選択肢

| 案 | 内容 |
|----|------|

### 私案２（この項目は新規のため主案）

**A 推奨。**  
能力は「出走前のビルド」、作戦時間は「今回の走り方」。役割が分かれ、考えて勝つ感が強い。  
B は締切直前の最適化合戦になりやすい。C は厳しすぎて β の試行錯誤を阻害しうる。

## 18. スタート時の操作

**状態:** 決定済（2026/09/27、ローカル簡易版から適用）

### 論点

一般的な競馬ゲームでは、ゲート開放のタイミングに合わせてボタンを押す形式が多い。  
本ゲームでは、反射神経によるタイミング入力は採用しない。カウントダウン中に開始時のノッチを選び、どの出力で飛び出すかの読み合いを重視する。

### 決定

| 要素 | イメージ |
|------|----------|
| **UI** | レース開始前のカウントダウンと、現在の開始出力ノッチ |
| **操作** | カウント中に上下でノッチを選ぶ。初期値は4 |
| **開始** | `START!` で、選択済みのノッチのまま全員が走行を開始 |
| **タイミング判定** | なし。出遅れ、開始ボーナス、開始ペナルティを設けない |
| **CPU** | 本実装のトレーナー判断までの簡易版では、開始ノッチ4で同じ発進計算を使う |

本番では、サーバーが共通の開始時刻を配り、全参加者が同じカウントダウンを表示する。CPUの開始ノッチは、将来トレーナーの作戦判断から決める。

## 28. 出力ノッチと空気抵抗モデル（ローカル実験の決定）

**状態:** 決定済（ローカル簡易レース限定。M5 オンラインと server は変更しない）

番号 23 はローカル簡易レースに使っている。この案は別項目。

ローカル簡易レースの実走を基に、ノッチ上限を6、空気抵抗を速度二乗式へ更新する。M5 オンラインの目標スピード方式と server は変えない。

### 決定

- 速度帯（ノッチごとの固定目標速度）は採用しない。
- ノッチは駆動力として扱い、速度に応じた抵抗との差分で加減速する。
- 転がり抵抗は `0.55 km/h/s` のまま、空気抵抗は速度二乗とする。2026-10-02、ユーザー判断で係数をそれまでの `0.00120` から `0.00204`（1.70倍）へ、ノッチ5の心拍上昇率を `5.4` から `7.0` へ仮採用した。2026-10-03、ユーザー判断でノッチ別心拍上昇率を `[0.0, 1.5, 2.5, 4.0, 6.0, 9.0, 13.0]` へ更新し、ノッチ1〜4も変更した。200超過後のペナルティ、最高速幅、空力と心肺の傾きは変えていない。
- 駆動力は `[0.0, 3.0, 3.5, 4.3, 5.0, 5.8, 7.2]` km/h/s。全ノッチは同じ「駆動力−転がり抵抗−空気抵抗」の式を使い、ノッチ帯ごとの特別処理は置かない。

心拍上では、ノッチ6を微調整用の強ノッチではなく、かなりキツい全力疾走として扱う。心拍上昇率13.0の現行設定では、通常心肺5がノッチ6を連続すると約16秒で通常上限200 bpmを超え、約24秒でオーバーヒート上限230 bpmへ到達する。ノッチは6段階を維持し、7・8などを追加して操作を忙しくしない。

### ねらい

- ノッチ1とノッチ2は最低速度40km/hでは抵抗が駆動力を上回り、床に留まる。ノッチ3から床を離れ、高速域では抵抗により自然に減速する。
- ノッチ6はスプリント用とする。最高速15・単独・ドラフトなしでは、40km/hから74.5km/hまで約25秒で近づき、75km/hが釣り合いになる（2026-10-02の係数 `0.00204` での計算）。
- 高速域では空気抵抗が自然に増え、ノッチ3〜5は段階的に減速し、ノッチ6だけが加速する。
- ドラフト中は空気抵抗が軽減され、低いノッチでも速度を維持しやすくする。

※ 空気抵抗の軽減・応答曲線・合成の適用はローカル出力方式だけとし、M5/server の駆動への適用は変更しない。一方、M5/server/ローカル共通の受給判定は、前方最小距離と横ずれ減衰を満たす効果範囲内の全前走者を対象とする規則へ更新済みである。

ローカル出力方式のドラフトは、効果範囲内の全対象の個別寄与を `draft_aggregation_exponent = 0.7` の p ノルムで合成する。2026-10-02、ユーザー判断でそれまでの `2.3` から仮採用した。指数が1未満のため、複数対象の合成は各寄与の合計を超え得る。1対象は指数の影響を受けない。直接と連鎖の合算受取率は上限で丸めない。ローカル実効率は、基準 `r = 受取率 / (wake_base_p + wake_speed_gain_p)` から `x = r^draft_response_exponent × 集団適性倍率` を作り、`x / (1 + x)` とする。2026-10-02、それまでの二乗のまま（100%を超え得る）から、効果が増えるほど100%へ近づく式へ変えた。固定の上限値は置かない。同じ日に、共有の連鎖減衰を `0.7` から `0.5` へ変え、最高速補正はドラフト後に残る空気抵抗と空力倍率を含めて計算するようにした。1／2／3対象の条件分岐や対象数上限は持たない。ドラフト判定・全対象選択・連鎖の共通規則は M5/server と揃えるが、実効率の応答曲線とローカル走行への適用はM5/serverへ反映しない。

### 操作性の正式採用（2026/09/27）

- 操作性は育成ステータスとして正式採用する。スタートダッシュ・巡航力・ラストスパートは引き続き独立ステータスにしない。

### コントローラー操作の暫定統一（2026/09/27）

- 左スティック左右／十字キー左右はライン移動、十字キー上下はローカルの出力ノッチおよび M4・M5 の目標スピード変更に使う。

- X は将来のブースト操作に予約する。現時点ではブースト本体が未実装のため、押しても走行性能は変えない。

### 基礎ステータス・属性・脚質補正の確定（2026/09/27）

- 基礎ステータスは8項目、各1〜10、合計40点、初期配分は全項目5とする。0は使わない。
- 地水火風はそれぞれ2項目へ各+2を付与し、属性補正対象だけ出走前の上限を12にする。
- レース中の有効値は、脚質の順位補正（全項目-1/0/+1）と4区間の脚質ボーナス（対象項目+2）を加え、1〜15へ収める。
- モチベーションは独立した性能補正として採用せず、脚質・順位・区間、心拍、スタミナ、接触による変化で表す。

### 心拍・スタミナ基本接続（2026/09/28）

- ローカル簡易レースで心拍・スタミナを走行計算へ接続する。心拍は共通 `100〜230 bpm`、通常上限 `200 bpm` とし、常に `ノッチ負荷−自然回復` の一つの式で更新する。心肺ステータス1〜15はノッチ別基礎負荷・自然回復率を連続補間する。正ノッチでは釣り合いによりノッチごとの定常域へ収束し、ノッチ0・負ノッチでは自然回復だけが働いて100 bpmへ漸近する。速度・空気抵抗は今回の心拍計算へ加えない。
- 心拍が高いほど燃料消費を増やし、スタミナ値は燃料タンク容量へ使う。同じノッチ・同じ心拍でのL/s消費は全員共通とする。ノッチ0・制動では心拍上昇や燃料回復を発生させない。
- 燃料容量は `5 + 3 × 有効スタミナ` L、負債下限は `-容量L`。2026-10-03、ユーザー判断で消費倍率 `1.30` を採用した。0未満では負債率に応じて推進など操作由来の効果を連続的に失効させる。オーバーヒート中は燃料消費倍率を心拍に応じて上げ、200超過率を時間で加重した負荷により推進効率を連続的に悪化させる。230 bpmで表示心拍が頭打ちになっても、超過負荷と性能低下は継続する。
- 接触・ブースト・急なノッチ変更による追加心拍負荷は、後続段階で同じ負荷入力へ追加する。

### 心肺・スタミナの身体負荷係数の仮採用（2026/10/01）

- **状態:** ユーザー承認による仮採用。心肺差の縮小（上昇基準 `13 / 20` 秒、自然回復基準 `27 / 22` 秒）と、スタミナを燃料タンク容量へ置き換える。容量は `5 + 3 × 有効スタミナ` L、消費は共通L/s。比較は標準1.15／高負荷1.30／強高負荷1.45で、2026-10-03にユーザー判断で `1.30` を採用した。開始画面の比較選択を変えないときは `1.30` で走る。
- 事前比較では現行と心肺縮小＋軽減40／45／50%を、単独数値走行128件と全頭CPU12レース、追加検証2レースで比較。身体負荷の役割分担として45%を候補にしたが、アカネ独走・後方脱落・約2分の勝ち時計・70km/h超の攻めは未解決。数十秒の遅れは今回再現できず、解決済みとは扱わない。
- 時間刻みを半分にすると一部CPUの完走時間が最大約2.8秒変化したため、細かな順位・時計差だけで係数を確定しない。キャラ個別の救済、CPU・速度の変更はこの仮採用に含めない。

### 加速力の役割整理と共通比較試験（2026/10/01）

## 29. 接触・押走りの将来仕様案

**状態:** 検討メモ（未実装・現行ローカル接触処理は変更しない）

横方向と前後方向の接触を、同じ押し返し処理にせず、レース上の意味を分ける案。

### 横方向：位置取りの競り合い

- 横移動先に他ぷるりんがいる場合、両者の**接触耐性**と**操作性**を基に、押し出される側と量を決める。
- 接触耐性が低い側は押し込まれやすく、接触中はスタミナ減少・心拍上昇などの負荷を受けやすい。
- 押し込み先にも別ぷるりんまたは柵があれば、そこで再度接触を判定する。逃げ場がなければ板挟みとして位置は動けず、両側接触の負荷を受ける。

### 前後方向：前方ブロックと押走り

- 前にぷるりんがいる場合は、その位置を通り抜けず、後続はそれ以上前進できない。
- 前後接触自体は接触耐性による押し合いにせず、後続のスタミナ・心拍へ追加ペナルティは掛けない。高い出力の一部が進行に使われず、空回りするだけとする。
- 後続の予定速度が前走者より高く、前後・横の接触距離内にいる場合、余った推進の一部を**押走り**として前走者へ短時間伝える。
- 押走りはドラフトとは別の小さな加速補正であり、前走者の空気抵抗軽減としては扱わない。効果は横ずれ・距離離れ・後続の速度低下で消える。
- 複数の後続による押走りは単純加算せず、合算した後に上限を設ける。

### 実装順

1. 現行の「重なる位置へは移動しない」前後ブロックを安定させる。
2. キャラの接触耐性・操作性が実装された後、横方向の競り合いと負荷を導入する。
3. その後、前後ブロックから算出する押走り補正を導入する。

現時点では、ドラフト＝「後ろが楽になる」、押走り＝「前が少し得をする」という役割分担を採用候補とする。
- 実際の係数・計算式は、基本ステータスをレースへ接続する実装段階で決める。
