## 1. 人型トレーナーを画面に出すか

**状態:** 未決

### 論点

参考画像（タイトル寄り）には人型キャラがいる。  
仕様上のプレイヤー役割は「トレーナー」だが、**画面上に人を出すか**は世界観の分岐点。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 人は出さない。UI・指示・名前だけがトレーナー |
| **B** | ロビー／結果画面だけ人型（またはシルエット）を出す |
| **C** | レース中もトラックサイドにトレーナーを表示 |

### 私案

**A（初期）→ 必要なら B。**  
レースの主役はぷるりん。人を出すと制作コストと世界観説明が増える。キービジュアル用の人は「宣伝イラスト」として切り分けるのが楽。

### 私案２

**同意（A 固定を長めに）。**  
β までは人型アセットを作らない。タイトル画像の人は「宣伝用・非公式設定」と割り切る。  
B に進むなら、シルエットやアイコン程度から。C はカメラ・同期・制作量が一気に増えるので見送り推奨。

## 2. 能力ポイントの総量・再配分ルール

**状態:** 未決

### 論点

「考えて勝つ」の中心が能力配分なのに、**何ポイント配れるか／後から変えられるか**が未定義。  
ポイント消費カーブ（高ステほど高い）も設計案から削除済みで、代替ルールも未定。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 固定プール（例: 合計 100）。作成時に配分。以降はレース用の作戦だけ変更可 |
| **B** | 固定プール＋「リセット」は冷却時間または回数制限付き |
| **C** | レース勝利などでプールが増える（成長）。見た目報酬と分ける |

### 私案

**A を基本、B を緩和策。**  
C は「育成で強い個体を作る」に寄りやすく、ガチャ無しでもパワーインフレしやすい。  
まず **総ポイント数と各ステの上限** を仮決めし、8 頭対戦で触って調整するのがよい。

**仮提案（議論用）:**

- 配分可能ポイント: 80〜100
- 各ステ上限: 100（属性ボーナスで実効が上振れ可）
- 極端ビルドは可能だが、何かが必ず欠ける

### 私案２

**A に寄せつつ、ルールを一段具体化する（最優先で詰める項目）。**

消費カーブを復活させるより、次の方が説明しやすい:

| ルール | 仮 |
|--------|-----|
| **基礎値** | 全ステに同じ初期値（例: 各 30） |
| **配分プール** | 追加で振るポイント（例: 40） |
| **上限** | 各ステ 100（属性ボーナスは別枠で実効加算） |
| **再配分** | β は無料リセット可（デバッグ・調整優先）。正式版で B（冷却／回数）へ |

理由: 「高ステほど高い」は体感しにくい／説明コストが高い。基礎＋プールなら極端ビルドも残しつつ、最低限の万能性でレースが壊れにくい。  
**数値は仮。8 頭プロトで必ず触って直す前提。**

## 3. 所持ぷるりん数・スロット

**状態:** 未決

### 論点

1 体だけだと愛着は出るが、距離・コース適性の「合わせる楽しさ」が弱い。  
複数だと管理 UI と命名・見た目の手間が増える。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 常時 1 体のみ |
| **B** | 最大 3 体（短／中／長向きなど） |
| **C** | 最大 8 体など多め（図鑑・コレクション寄り） |

### 私案

**β は B（最大 3）。**  
設計の「どのレースに合わせるか」と相性が良い。C は見た目コレクションが乗ってからでよい。

### 私案２

**同意（B）。さらに「作成順」を決める。**

- アカウント作成直後は **1 体だけ**（チュート負担を減らす）
- 練習クリア or 数走後に 2・3 枠解放
- 属性変更可否（#15）とセットで決めると、3 体の意味がはっきりする

C は模様・表情コレクションが充実してから。β で枠を広げすぎない。

## 4. レース報酬（ガチャなしで何を渡すか）

**状態:** 未決

### 論点

能力はポイント配分で決める方針なので、報酬でステを直接強くしすぎない方がよい。  
一方、何も無いと「次のレース」以外の目的が薄い。

### 選択肢（組み合わせ可）

| 報酬種 | 内容 | 能力への影響 |
|--------|------|--------------|
| 見た目パーツ | 目・口・眉・ほっぺ | なし |
| 模様 | 属性・季節・イベント | なし |
| 称号・記録 | 連勝、特定脚質など | なし |
| 通貨 | 改名・スロット解放など | 間接のみ |
| 能力ポイント | プール増加 | **あり（要注意）** |

### 私案

**見た目・称号・記録を主報酬。能力ポイント増加はβでは入れない（またはごく少量）。**  
「同じ条件から作戦で勝つ」を守る。

### 私案２

**能力ポイント増加は β・正式とも「原則なし」に寄せる（私案より厳しめ）。**

| 渡す | 渡さない |
|------|----------|
| 表情・模様・称号・戦績 | ステ強化、ステ解放ガチャ |
| 改名チケット等の軽通貨（任意） | 勝たないと強くなるループ |

理由: 「ごく少量」は後からインフレの抜け穴になる。継続欲は **見た目と記録** で足りる設計に寄せた方が、いまの方針と一貫する。  
順位表・リプレイ視聴・脚質別成績など「見る報酬」も有効。

## 5. ソロ練習・オフラインの範囲

**状態:** 未決

### 論点

オンライン受付サイクル前提だと、人が少ない時間帯や開発初期に触れない。  
CPU 補充は開催側である程度カバー済みだが、**自由練習**があるかは別問題。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | オンラインのみ（締切時 CPU 補充） |
| **B** | 練習モード（CPU 8 頭、結果はランキング非反映） |
| **C** | 完全オフラインのローカル対戦も可 |

### 私案

**B を早めに用意。**  
操作・カメラ・配分の習熟用。C は後回しでよい。

### 私案２

**同意（B を Phase 寄りの早めに）。条件を具体化。**

- 距離・コースを選べる（配分の検証用）
- 結果はランキング／レーティング非反映
- CPU の強さは「標準」固定でよい（難易度多段は後）
- #14（CPU の見え方）と同時に決めると練習の意味が伝わる

C（完全オフライン）は同期テストが終わってからで十分。

## 6. マッチングとレーティング

**状態:** 未決

### 論点

10 分サイクル＋受付は「同時開催のロビー」型。  
レーティングを入れると公平性は上がるが、待ち時間と実装が重い。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | レーティングなし。来た人＋CPU で 8 頭 |
| **B** | 簡易レート（勝ち越しで帯が変わる程度） |
| **C** | 本格 MMR マッチ（同レート帯優先） |

### 私案

**β は A。**  
人が少ないうちは C は成立しにくい。データが溜まってから B を検討。

### 私案２

**同意（β＝A）。「公平さ」はレート以外で出す。**

- 受付締切時の CPU 補充で常に 8 頭（設計案どおり）
- 戦績は見えるが、マッチ分けには使わない
- 実力差の不満が出たら、先に **練習** と **作戦フェーズの説明** を厚くする

B は同時接続が安定してから。C は長期見送りでよい。

## 7. 実況・SE・BGM の方針

**状態:** 未決

### 論点

配信映え・「競馬感」には音が効く。一方で初期コストが大きい。  
命名の「読み」将来枠とも関係する。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | β は SE＋BGM のみ。実況なし |
| **B** | 簡易実況（定型テキスト or 短いボイス） |
| **C** | 本格実況（名前読み上げあり） |

### 私案

**A → 余裕があれば B。**  
C は読みルールと音声コストが先に必要。

### 私案２

**同意。優先は SE（ブースト・接触・ゴール）＞ BGM ＞ 実況テキスト。**

配信映えはカメラ切替・ミニマップ・順位 UI の方が先に効く。  
B をするなら「ボイスなしのテロップ実況」がコスパ良い。C は命名の「読み」が決まってから。

## 8. 対応プラットフォーム

クライアントは Godot。どこを第一ターゲットにするかで UI・操作が変わる。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | PC（キーボード／パッド）優先 |
| **B** | PC ＋ Web エクスポート |

### 私案

**A を第一。Web は β 後期の候補。モバイルは操作（指示中心）とは相性が良いが、後回し。**

### 私案２

ただし **UI を PC 前提の小さい文字だらけにしない**（後の Web／モバイルに効く）。  
B/C のための「マルチ解像度」はレイアウトを組む段階で軽く意識する程度でよい。

## 9. 世界観の最小セット

**状態:** 未決

### 論点

メカニクスは厚いが、「なぜぷるりんが走るのか」がほぼ無い。  
長くなくても、ロゴ・タイトル・NPC の口調が決まる。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 世界観ほぼ無し。競技としてのレースだけ |
| **B** | 1 段落の設定（例: ぷるりん競技会が街の祭り） |
| **C** | 本格 lore（歴史・地域・組織） |

### 私案

**B。**  
C は world スキルで雑談しながら育てればよい。今は「かわいく走る理由」が一言あれば足りる。

**たたき台:**

> ぷるりんたちは、身体能力と息の合わせで競う「ぷるりんレース」を楽しむ。  
> トレーナーは作戦を託し、観客は集団の駆け引きに沸く。勝敗は運より判断。

### 私案２

**同意（B）。たたき台を設計案の「プロジェクト概要」近くへ移す候補にする。**

人型トレーナーを出さない（#1＝A）なら、世界観文も **ぷるりん主役** のまま維持。  
C に走るのは、模様・大会名・コース名が欲しくなってからでよい。

## 10. カーブ時のカメラ振り（設計案で保留）

**状態:** 未決（設計案「カメラ・視点・ミニマップ」で保留）

### 論点

カーブでカメラを外側へ振ると臨場感は出るが、酔い・操作の見通しが変わる。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 振らない（常に進行方向基準の安定カメラ） |
| **B** | 弱く外側へ（オプションでオフ可） |
| **C** | アングルごとに挙動を変える |

### 私案

**プロトは A。**  
酔いに敏感なジャンルでもあるので、後から B をオプション追加が安全。

### 私案２

**同意（A）。「振り」よりミニマップと前後スライド選択を先に固める。**

設計案ですでにカメラ切替・他個体視点があるので、カーブ振りは後回しでも体験は成立する。  
B を入れるなら **デフォルトオフ**。

## 12. 観戦の公開範囲

**状態:** 未決

### 論点

リプレイ基盤と観戦は近い。誰が何を見られるかはサーバー負荷とプライバシーに関わる。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 自分が関係するレースのみ観戦・リプレイ |
| **B** | 開催中の全レースを誰でも観戦可 |
| **C** | 公開／非公開をホスト（または参加者）が選ぶ |

### 私案

**β は B（少人数なら単純で配信にも良い）。**  
規模が大きくなったら負荷を見て A や部屋選択に寄せる。

### 私案２

**同意（β＝B）。ただし「観戦専用クライアント負荷」を測る前提を書く。**

同時 5 レース × 観戦者増は、帯域より CPU／配信対象の選別が先に効く可能性。  
実装は「ロビーから開催中レース一覧 → 観戦」で単純に。C は要望が出てから。

## 13. 作戦フェーズで何をロックするか（新規）

**状態:** 未決

### 論点

開催サイクルに「出走確認・作戦」時間がある。  
ここで **配分・脚質・指示プリセットのどこまで変えられるか** が未定義だと、公平性と UI が曖昧。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 作戦時間は脚質プリセットと初期指示のみ。能力配分は事前のみ |
| **B** | 作戦時間に能力の微調整も可 |
| **C** | ゲートイン後は指示のみ（脚質もロック） |

### 私案２（この項目は新規のため主案）

**A 推奨。**  
能力は「出走前のビルド」、作戦時間は「今回の走り方」。役割が分かれ、考えて勝つ感が強い。  
B は締切直前の最適化合戦になりやすい。C は厳しすぎて β の試行錯誤を阻害しうる。

## 14. CPU 補充の透明性（新規）

**状態:** 未決

### 論点

締切時 CPU 補充で常に 8 頭、は設計案にある。  
プレイヤーに **どれが CPU か** を見せるかで、対戦の印象が変わる。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | CPU と明示（名前に印、リストで色分け） |
| **B** | 区別なし（全部同じに見える） |
| **C** | 練習のみ明示、本番レースは非表示 |

### 私案２

**β は A。**  
少人数期に「人間だと思ったのに CPU」への不信を避ける。  
本格稼働で人が埋まってきたら C や B を再検討。

## 15. 属性の変更可否（新規）

**状態:** 未決

### 論点

属性は能力補正を持つ。作成後に変えられると「合わせる」は楽だが、個体の意味が薄れる。

### 選択肢

| 案 | 内容 |
|----|------|
| **A** | 作成時に固定。以降変更不可 |
| **B** | 冷却付きで変更可 |
| **C** | 見た目模様だけ変えられ、属性補正は固定 |

### 私案２

**A（作成時固定）。**  
所持 3 体（#3）と組み合わせると、短・中・長や属性違いを「別個体で持つ」形になりきれい。  
模様・表情はいつでも変更可（能力非影響の方針どおり）。
